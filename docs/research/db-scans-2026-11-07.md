# Database scans: before and after the indexes (#392)

Measurements of the startup and daily scans the audit named. Conductor's own database grew to
12 GB (D006), so the queries were timed on a database of the same order, built through the app's
real migrations.

## Instrument and volume

`scripts/measure/db-scans.ts` builds a file database with every migration applied, in a folder the
run creates and deletes at the end, even on failure. It uses the app's pragmas (WAL, foreign keys on). Run it
with:

```
bun scripts/with-run-dir.ts bun scripts/measure/db-scans.ts
```

The script also drains the daily tool-output cut in committed batches (to mark every cut row), then
times one more batch, so the "after the cut already ran" cost is measured rather than guessed.

The instrument is checked first on a known case. A lookup on the primary-key column uses a
covering index and returns in under a millisecond; a filter on `length(content)`, which no index can
answer, scans the whole table:

| Known case                     | Plan                                                                       | Time      |
| ------------------------------ | -------------------------------------------------------------------------- | --------- |
| indexed: one chat's events     | SEARCH session_events USING COVERING INDEX idx_session_events_turn         | 0.06 ms   |
| unindexed: `length(content)`   | SCAN session_events                                                        | 1335.57 ms |

Volume and why:

- 20 repositories, 500 workspaces, 5,000 chats, 2,000,000 events. 400 events per chat covers
  months of tool-heavy agent work.
- Events spread over 400 days, so about 92% are older than the 30-day tool-output age limit, and
  the daily scan really does meet the whole history.
- Event mix: 25% `user_message`, 25% `turn_ended`, 50% `agent`. Half the agent events carry a tool
  result. Tool outputs are 92% small (100 to 1,500 characters), 7% medium (5,000 to 40,000) and 1%
  large (120,000 to 300,000), close to what a shell command or a file read returns.
- 30,000 attachments, 10,000 terminals, 20 sections, 500 section members, 300 backlog rows, and a
  chat tab open on every workspace. One workspace in 25 is archived, so the compact query has work.

Before: 3.36 GB. After: 3.46 GB (the new index, about 3% more).

CREATE INDEX idx_session_events_unreverted_turn
  ON session_events(reverted_at, session_id, turn_id, type, idx);

## Reading `compacted_at` (#393)

The daily cut now reads `session_events.compacted_at`, the one home of "this event was compacted".
It skips a row the job already cut (`compacted_at IS NULL` in the candidate query), and the
archived-chat compaction marks its `turn_ended` event with the same column instead of the JSON
`$.compacted` flag. The script drains the cut in committed batches to mark every cut row, warms
the page cache, then times one more batch:

| Query | Plan | Time |
| --- | --- | --- |
| `cutToolOutputs`, one batch on a fresh database (no row marked) | `SEARCH session_events USING INTEGER PRIMARY KEY (rowid=?); ...; SCAN e; SCAN i EXISTS ...` | 244.08 ms |
| `cutToolOutputs`, one batch after the cut already ran (25 batches drained, 5,000 rows marked) | the same plan | 238.90 ms |

The marker does its job: the next batch changes no rows. The time barely moves because the cost is
scanning 2,000,000 old events and reading their `length(content)`, not the JSON of the 5,000 rows
already cut. A saving needs the job to stop scanning history older than the last run (a watermark),
not another column check. The job now keeps that watermark: `data_lifetime_tool_outputs_watermark`
holds the age cutoff of the last finished pass, and the next run looks only at events at or after
it, so a daily run meets one day of events that crossed the line instead of the whole history.

`findCompactableTurns` also reads `compacted_at` now, so a turn compacted on an earlier run is
found by a column comparison rather than `json_extract`. Its time stays 0.42 ms.

## What the measurement rejected

**Do not index the daily `cutToolOutputs` scan.** An index on `session_events(type, received_at)`
was tried first. The planner used it, but the query orders by `rowid`, so the index forced a sort
and the batch went from 243 ms to **2,481 ms**. The same index also made `findCompactableTurns`
worse (0.53 ms to **702 ms**), because that query had been using the primary-key order to stop at
its `LIMIT 200`. Both indexes were removed. The daily scan's cost is the JSON it reads with
`json_extract` and `json_each`, which an index on `type` and `received_at` cannot avoid.

**Do not index the small tables.** Every other filter the audit named scans a table small enough
that the scan is under 1.4 ms at this volume. An index would add write cost to rows the app writes
often (attachments, terminals, workspaces) and save a millisecond.

**Partial and non-covering variants of the repair index** were tested on a 400,000-event sample.
A partial index `(session_id, turn_id, type, idx) WHERE reverted_at IS NULL` was not chosen by the
planner at all. The covering index above was chosen and made the query about 25% faster on the
sample; on the full database it halved the time.

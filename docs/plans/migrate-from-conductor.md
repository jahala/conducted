# Moving from Conductor to Conducted

Issue #353. Decisions D100, D124, D130 and D132. Built by APP-17; chat history by APP-18, once the spike below met its mark. Someone who uses Conductor can move to Conducted, keep their projects, workspaces, chats, settings and scripts, and still go back to Conductor at any time.

## Safety rules

These hold for every step, and each has a test (section "Checks").

1. **Conductor's files are only read.** Its database and write-ahead log are copied as bytes into a folder the import owns, and only that copy is opened. SQLite is never pointed at Conductor's files, because opening a database, even read-only, creates or writes files beside it (D124). Every later step reads that copy. Nothing in `~/Library/Application Support/com.conductor.app/`, in a repo's `conductor.json` or `.conductor/`, or in a worktree is written, moved, renamed or locked.
2. **A dry run comes first.** The import lists what it will bring over, what it cannot, and why, before it changes anything in Conducted. The user then chooses to go ahead.
3. **All or nothing.** Conducted's own database is written in one transaction. A failure rolls it back, so Conducted's data is as it was. Keychain entries the import made are removed on rollback. Chat history is written after that transaction commits, in one transaction per chat: a chat comes over whole or without its history, never half of it.
4. **Checked after.** The import counts each kind of item before and after, and opens one sample of each (a workspace's folder, a chat's history, a setting). A count that differs fails the import and rolls it back.
5. **Worktrees stay where they are.** A workspace keeps its folder and branch; Conducted points at the folder. Nothing on disk moves.
6. **Secrets never show.** Where Conductor keeps an environment variable's value in its database, the Rust shell moves it straight from the copy into the macOS Keychain, as ours are kept (SET-04); the value never reaches the web view. In Conductor's release builds the value is in Conductor's own Keychain item instead (services-map.md 4.2.8), which the import does not read, so such a variable is listed in the dry run to enter again. Values never appear in the dry run, a log or an error.
7. **Once per item.** Each imported row keeps Conductor's id as its own, so a second import skips what is already there and adds only what is new (D124).

## Scripts and `CONDUCTOR_*` names

D027 stays: Conducted sets only `CONDUCTED_*` names, with no alias. When the import writes `.conducted/settings.toml`, it renames every `CONDUCTOR_` variable in the scripts it copies to `CONDUCTED_`, and the dry run shows each rename. A script file in the repo that reads a `CONDUCTOR_*` name (for example `./scripts/setup.sh`) belongs to the user, so the import does not edit it: the dry run lists the file, the line and the new name to use.

## Where it lives

- The reading and mapping are pure functions in the desktop app's `core/conductor-import/`: Conductor's rows in, our rows and a list of what was left out. They take the database copy as a value and do no I/O. Chat history maps in the sidecar (`packages/sidecar/src/import/conductor-history.ts`), beside the Claude translator it uses.
- The Rust shell makes the read-only copy and moves secrets into the Keychain.
- The user starts it from Settings (General, "Import from Conductor") and on first launch when Conductor's folder exists. The exact place follows D098: Conductor has no such control, so it goes where a first-run import most logically sits in Conductor's layout, and docs/design.md names it.

## Chat history

APP-18, D130. The history of each Claude chat comes over after the rows have committed.

- **Which chats.** A chat brings its history when its agent has a mapping (`CONDUCTOR_MAPPED_AGENTS`, Claude today) and the chat is in Conducted with no event of its own: a chat this import brings, or one an earlier import brought without history. A chat that holds any event already has its history or turns of its own, and nothing is added. So a second import adds nothing, and a chat whose history failed gets it on the next import. Codex, Cursor and ACP chats have no mapping yet: they come over (or stay behind) as before, without history, and the dry run counts them by agent.
- **What the dry run says.** The chats whose history comes and their rows, the chats that already have it, the chats of each agent with no mapping yet, and the chats that stay behind, whose history stays with them. A row is one sent `session_messages` row; queued rows are not history.
- **Disk space (D132).** The dry run reads and maps each chat it would bring, writes nothing, and sizes every event as the writer stores it, in SQLite's pages and indexes. It shows that size beside the free space on the disk that holds Conducted's database, which the Rust shell reads (`app.databaseFreeBytes`). The import needs the history, the largest chat twice more (once for SQLite's journal and once for the chat's staging, D136), and 2 GiB to spare. When that is more than is free, the dialog says so with both numbers and offers Try again instead of Import. The import reads the free space again when it starts, and refuses before it writes anything.
- **How a chat is read.** In two reads of the copy, so memory holds one read and never a chat. First every sent row of the chat without its content, 5,000 at a time in rowid order; the sidecar's mapper keeps only each row's place, times and size, and sets the order Conductor shows. Then the rows themselves, at most 1,000 holding at most 2,000,000 characters at a time, in that order; each read's events are written before the next. The mapping lives in the sidecar (`packages/sidecar/src/import/conductor-history.ts`), so the import reaches it over RPC (`indexConductorHistory`, `mapConductorHistory`, `closeConductorHistory`). Neither read needs an index on Conductor's table.
- **How a chat is written.** Each read's events go into a staging, one statement per read, outside any transaction. The staging is a temporary database that no reader of the chat sees, and SQLite deletes it when it is detached after the chat, or when the app closes. Then one transaction per chat copies the staged events into the chat in one statement, counts them and reads the first back before it commits. So the app's own writes wait for SQLite's copy of one chat, never for the chat's reads and mapping (D136). A failure rolls that chat back: it stays imported without history, the outcome names it with the reason, and the next chat goes on. A chat that gained an event since the dry run is left as it is.
- **What the events hold.** An agent event keeps no `raw` payload: the original is Conductor's row, which stays in Conductor's database (D132). Each turn ends with a `turn_ended` event, as our runner ends one: its last result decides success or error, and a turn with no result ends `unrecorded`, which our chat shows nothing for, as Conductor shows nothing. Without an end, our chat would show every imported turn as stopped. An event's `at` is Conductor's time; it is received at the import's time, so the data lifetime job ages it as an event received at import.

## The spike first

Before the import is built, a spike maps chat history on real data.

- Data: a backup copy of a real Conductor database (rule 1). The owner's own database is the only one we have, so the owner says yes before it is read (see the report).
- Pass mark, written before the run: at least 99% of the `session_messages` rows in the sampled chats map, and every chat that maps shows the same visible messages in the same order as Conductor. A row maps when the mapping reads it; a row Conductor's chat does not show (a turn with no user message, `/compact`, the "Compacted" reply beside a compaction) maps to nothing and is counted apart.
- What "the same visible messages" means, since 2026-11-11: per turn, the user's message and steers, then the main agent's text blocks and tool cards, compared by their content with white space folded. Conductor's side follows its chat's own rules (research frontend.md section 5, "What one turn shows"). Our side is the turns our chat's turn builder makes of the mapped events. Thinking, tool output, errors and notices are not compared, and neither is how either chat folds or nests what it shows.
- Why the wording changed: the first run (2026-11-07) counted every `session_messages` row as one message. Conductor writes a row for each streamed block, tool call and tool result, so even a hand-built chat that reads the same on both sides failed (10 rows against our 7 messages). The mark now compares what a reader sees, and the spike checks itself on such a chat before it is trusted (`scripts/conductor-import/spike.test.ts`).
- Chats of an agent the mapping does not handle yet (Codex today; Cursor and ACP too) are counted apart as "not mapped yet". They are left out of both halves of the mark, so "the sampled chats" means the sampled chats the mapping handles. Their history cannot come over until their translator exists; the spike's count keeps that gap in view.
- Kill criterion: below that, chat history does not come over. Chats still resume from the agent's transcript, and the dry run says history was left out.
- Source, since 2026-11-11 (issue #512): every chat's history is read from `session_messages`, the table Conductor's chat reads. The first runs mapped `session_events`, but Conductor began writing events partway through. On the owner's copy, 301 of 359 chats have messages and 41 have any events, and in 11 of 24 sampled chats most messages predate the first event. Events cannot rebuild turns they never recorded. The spike also counts chats that have events but no messages, the only history this source could miss.
- How to run it: `bun scripts/conductor-import/spike.ts <path-to-a-conductor-db-copy> [--sample N]`. It clones the copy into its own temporary folder, maps every chat that has messages (or N of them, spread evenly) with the sidecar's mapping, and prints counts only.
- Result: the lead's run on a copy of the owner's database on 2026-11-11 met the mark: all 288 Claude chats read the same as in Conductor, and 100% of 3,172,282 rows map (#555). The spike runs the same mapper the import runs (`mapConductorMessages` over rows in memory).

## Checks

- A test builds a Conductor database from `conductor-schema.sql` with known rows, runs the import, and compares counts and samples.
- A test watches the Conductor folder's files (size, modified time, a hash) before and after, and fails on any change.
- A test fails the import part-way and checks that Conducted's database and Keychain are as they were.
- A test runs the import twice and checks that nothing is doubled.
- A test checks that no secret value appears in the dry run, the log or an error.

- Chat history (APP-18): a Claude chat of several turns comes over and our chat shows its turns; a Codex chat comes without history; a chat whose history fails part-way is left without it, named, and the others are whole, and the next import brings it; a second import adds nothing; a chat used since the dry run is left as it is; an imported agent event keeps no `raw`.
- Disk space (D132): the dry run says the space chat history takes, the space it needs and the space free; an import the disk has no room for refuses before it writes anything and leaves Conducted as it was. The estimate is never below what the database grows by and at most 5% above, on four shapes of made-up chats with UUID ids (`conductor-import.space.container.test.ts`).
- A chat of 200,000 rows comes over with the heap the import retains within 64 MiB and flat while the rows are read, in one read of the copy per page (`conductor-history.size.container.test.ts`).
- At full size (#556): `bun scripts/conductor-import/measure.ts <path-to-a-conductor-db-copy>` clones the copy into a folder of its own and runs the real import on the clone into a scratch Conducted database there. It uses the real container, the Node stand-in for the Rust shell and the real sidecar process. It prints counts, timings and sizes only: the dry run's counts, the dry run's and the import's time, the five slowest chats as rows and seconds, the longest hold of the database queue by a transaction and by one statement outside a transaction, peak resident memory of the import's process and the sidecar in each stage (the dry run, the import, and opening the largest chat, which loads every event of it; sampled every 250 ms), the time to open the largest chat and build its turns, and the dry run's disk space figures beside the scratch database's file and journal before and after the import, so the estimate is checked against real data (D132). The Node stand-in clones Conductor's database as the Rust shell does, so on APFS the copy takes no space. Nothing outside its folder is written but the sidecar's socket, in a short folder of its own in /tmp because a socket's path holds about 104 bytes: a settings file the import writes into a project is kept in the run's folder, and only `git worktree list` and `lsof` reach the shell. Both folders are removed on every ending. Its test runs it on a made-up database with a chat of 200,700 rows and 338 million characters (`measure.test.ts`). It checks that the database file grows by the dry run's estimate, within 5% above, that the journal stays within the room the dry run asked for it, and that while the import runs the import process's memory rises less than 400 MB and the sidecar's less than 512 MB (#598).

The history checks and the first five are in `apps/desktop/src/core/conductor-import/conductor-import.container.test.ts`, through the real container. The Rust copy has its own tests in `conductor_import.rs`, and the Platform contract runs the copy on real files through the Node bindings (`conductorImport.copy-read`).

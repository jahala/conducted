# Moving from Conductor to Conducted

Issue #353. Decisions D100 and D124. Built by APP-17; chat history (APP-18) waits for the spike below. Someone who uses Conductor can move to Conducted, keep their projects, workspaces, chats, settings and scripts, and still go back to Conductor at any time.

## Safety rules

These hold for every step, and each has a test (section "Checks").

1. **Conductor's files are only read.** Its database and write-ahead log are copied as bytes into a folder the import owns, and only that copy is opened. SQLite is never pointed at Conductor's files, because opening a database, even read-only, creates or writes files beside it (D124). Every later step reads that copy. Nothing in `~/Library/Application Support/com.conductor.app/`, in a repo's `conductor.json` or `.conductor/`, or in a worktree is written, moved, renamed or locked.
2. **A dry run comes first.** The import lists what it will bring over, what it cannot, and why, before it changes anything in Conducted. The user then chooses to go ahead.
3. **All or nothing.** Conducted's own database is written in one transaction. A failure rolls it back, so Conducted's data is as it was. Keychain entries the import made are removed on rollback.
4. **Checked after.** The import counts each kind of item before and after, and opens one sample of each (a workspace's folder, a chat's history, a setting). A count that differs fails the import and rolls it back.
5. **Worktrees stay where they are.** A workspace keeps its folder and branch; Conducted points at the folder. Nothing on disk moves.
6. **Secrets never show.** Where Conductor keeps an environment variable's value in its database, the Rust shell moves it straight from the copy into the macOS Keychain, as ours are kept (SET-04); the value never reaches the web view. In Conductor's release builds the value is in Conductor's own Keychain item instead (services-map.md 4.2.8), which the import does not read, so such a variable is listed in the dry run to enter again. Values never appear in the dry run, a log or an error.
7. **Once per item.** Each imported row keeps Conductor's id as its own, so a second import skips what is already there and adds only what is new (D124).

## Scripts and `CONDUCTOR_*` names

D027 stays: Conducted sets only `CONDUCTED_*` names, with no alias. When the import writes `.conducted/settings.toml`, it renames every `CONDUCTOR_` variable in the scripts it copies to `CONDUCTED_`, and the dry run shows each rename. A script file in the repo that reads a `CONDUCTOR_*` name (for example `./scripts/setup.sh`) belongs to the user, so the import does not edit it: the dry run lists the file, the line and the new name to use.

## Where it lives

- The reading and mapping are pure functions in the desktop app's `core/conductor-import/`: Conductor's rows in, our rows and a list of what was left out. They take the database copy as a value and do no I/O. Chat history maps in the sidecar (`packages/sidecar/src/import/conductor-history.ts`), beside the Claude translator it uses.
- The Rust shell makes the read-only copy and moves secrets into the Keychain.
- The user starts it from Settings (General, "Import from Conductor") and on first launch when Conductor's folder exists. The exact place follows D098: Conductor has no such control, so it goes where a first-run import most logically sits in Conductor's layout, and docs/design.md names it.

## The spike first

Before the import is built, a spike maps chat history on real data.

- Data: a backup copy of a real Conductor database (rule 1). The owner's own database is the only one we have, so the owner says yes before it is read (see the report).
- Pass mark, written before the run: at least 99% of the `session_messages` rows in the sampled chats map, and every chat that maps shows the same visible messages in the same order as Conductor. A row maps when the mapping reads it; a row Conductor's chat does not show (a turn with no user message, `/compact`, the "Compacted" reply beside a compaction) maps to nothing and is counted apart.
- What "the same visible messages" means, since 2026-11-11: per turn, the user's message and steers, then the main agent's text blocks and tool cards, compared by their content with white space folded. Conductor's side follows its chat's own rules (research frontend.md section 5, "What one turn shows"). Our side is the turns our chat's turn builder makes of the mapped events. Thinking, tool output, errors and notices are not compared, and neither is how either chat folds or nests what it shows.
- Why the wording changed: the first run (2026-11-07) counted every `session_messages` row as one message. Conductor writes a row for each streamed block, tool call and tool result, so even a hand-built chat that reads the same on both sides failed (10 rows against our 7 messages). The mark now compares what a reader sees, and the spike checks itself on such a chat before it is trusted (`scripts/conductor-import/spike.test.ts`).
- Chats of an agent the mapping does not handle yet (Codex today; Cursor and ACP too) are counted apart as "not mapped yet". They are left out of both halves of the mark, so "the sampled chats" means the sampled chats the mapping handles. Their history cannot come over until their translator exists; the spike's count keeps that gap in view.
- Kill criterion: below that, chat history does not come over. Chats still resume from the agent's transcript, and the dry run says history was left out.
- Source, since 2026-11-11 (issue #512): every chat's history is read from `session_messages`, the table Conductor's chat reads. The first runs mapped `session_events`, but Conductor began writing events partway through. On the owner's copy, 301 of 359 chats have messages and 41 have any events, and in 11 of 24 sampled chats most messages predate the first event. Events cannot rebuild turns they never recorded. The spike also counts chats that have events but no messages, the only history this source could miss.
- How to run it: `bun scripts/conductor-import/spike.ts <path-to-a-conductor-db-copy> [--sample N]`. It clones the copy into its own temporary folder, maps every chat that has messages (or N of them, spread evenly) with the sidecar's mapping, and prints counts only.

## Checks

- A test builds a Conductor database from `conductor-schema.sql` with known rows, runs the import, and compares counts and samples.
- A test watches the Conductor folder's files (size, modified time, a hash) before and after, and fails on any change.
- A test fails the import part-way and checks that Conducted's database and Keychain are as they were.
- A test runs the import twice and checks that nothing is doubled.
- A test checks that no secret value appears in the dry run, the log or an error.

The five are in `apps/desktop/src/core/conductor-import/conductor-import.container.test.ts`, through the real container. The Rust copy has its own tests in `conductor_import.rs`, and the Platform contract runs the copy on real files through the Node bindings (`conductorImport.copy-read`).

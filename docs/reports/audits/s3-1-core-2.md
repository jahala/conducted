## REV-04 Sync review comments with GitHub

- MUST `core/container.ts:752` (`onPullRequestChanged`): a failed sync is only written to the log (`Could not sync review comments`). `ReviewService.syncFromGithub` sets no `errors` entry, so the user never learns that comments stopped syncing. This is the "error that is only logged" shape from engineering.md. Fix: have `syncFromGithub` put the failure in `ReviewState.errors[workspaceId]` (the store already has that slot) and show it where the comments show, so a stale list is not read as current.
- MUST `features/git-panel/checks/ChecksTab.tsx:136-146`: the screen calls `services.review.resolveOnGithub` directly instead of going through `actions.comments.*`, the way every other action in the same file does. `useActions` is the screen-to-service door (architecture.md). It also means the unresolve path (`resolved === false`) falls through to the local-only `setResolved`, so a GitHub thread is shown unresolved locally while GitHub still says resolved, and the next sync flips it back. Fix: add `Actions.comments.resolveOnGithub` and either hide "Unresolve" for GitHub threads or reject it with a plain message.
- LATER `core/services/review.ts:527-563`: when one list is a normal skip (`github_pr_missing`) and the other fails with a real error, the skip error is returned last (`if (!threadsRead.ok) return threadsRead`). The caller gets "no pull request" instead of the real failure. Fix: return the first non-skip error.
- LATER `core/services/github.ts:2276`: a sync starts only when the PR's `updatedAt` changes. GitHub does not always bump the PR's `updatedAt` when a review thread is resolved or a comment is edited, so those can wait for the next unrelated change. No test covers it. Fix: also sync on a timer while the Checks tab is open, or when the tab opens.
- LATER `core/services/github.ts:2982-2997` (`#reviewSyncTarget`): the remote is read from `found.remote`, but the GraphQL calls use gh's own `{owner}/{repo}` placeholders. With a fork that has several remotes they can name different repositories. Fix: pass owner and name from the parsed remote as `-f` variables.
- LATER Tests: `core/s1-core-2.join.test.ts:358-362` and `core/services/review.rev-04.test.ts` spy on `GithubService.readReviewThreads`, `readGeneralComments` and `resolveReviewThread` with canned answers. That is a seam, but the GraphQL answer parsing is then only covered by `github.rev-04.test.ts`. "Loads both lists in parallel" has no test (nothing fails if the two reads run one after the other). "Sync after a poll shows a change" tests the first poll and a changed `updatedAt`, but not that an unchanged poll starts no sync. No test has two overlapping `syncFromGithub` calls.
- Specs and headers: `review.ts`, `github.ts` and `gh-commands.ts` headers match the code. Duplication: none found. Checklist items without a test that would fail: "parallel", "unresolve stays consistent" (not a checklist item, but a gap).

## RUN-02 Spotlight

- MUST `features/scripts-panel/run/RunTab.tsx:140`: `isSpotlight: false` is hard-coded, and `core/services/run-scripts.ts` adds no synthetic Spotlight action to `RunState.actions`. So "Start spotlight", "Stop spotlight" and "The run list shows a synthetic Spotlight action" can never appear, and nothing in the live UI calls `actions.run.startSpotlight` (`RunTab.tsx:173` is dead). The spotlight header and `run-button-label.ts` claim the button. The container test (`spotlight.run-02.test.ts:510-531`) mocks `spotlight.start` and calls the action directly, so it passes without any UI path. Fix: when the repository has `spotlightTesting` on, the run list gets a Spotlight entry; `RunTab` passes `isSpotlight` from it; test it with the real container and a click on the button.
- MUST `core/services/spotlight.ts:289-306` (`#stopWorkspace`): the spec is "kill the sync, wait the 20 s watchdog, restore pre-spotlight and delete the ref only on success". When `terminals.stop` returns `run_stop_unconfirmed` (the process is still alive after 20 s), the code still restores the root, deletes the ref, clears the active state and only then returns the stop error. A sync that is still running can overwrite the restored root, and the app now believes Spotlight is off. Fix: if `stopped` failed, do not restore or deactivate; return the error and keep the ref. Add a test where `stop` returns the unconfirmed error.
- MUST `core/services/spotlight.ts:271-274`: when the Spotlight terminal exits on its own (the script crashes, the user closes the terminal, `watchexec` is missing; `bin/spotlighter.sh` is still the RUN-08 stub and exits 64), the handler only calls `#deactivate`. The root is not restored, the `pre-spotlight` ref stays, `#roots` keeps its entry, and the Run tab shows Spotlight as stopped while the root still holds workspace files. The header says stopping restores the root. Fix: on exit, run the same restore as `#stopWorkspace`, and surface a failure. Test: terminal exit with no stop call.
- MUST Checklist item "The user is told that the root's branch pointer moves while Spotlight runs" (services-map 5A.2.5) has no code and no test. The header line "the root's branch pointer moves while Spotlight runs" is explanation only; nothing is shown. Fix: show the notice when Spotlight starts (a toast or a line in the Run tab) and test it.
- MUST Checklist item "Turning Spotlight testing on or off can fail with 'Failed to update spotlight testing'" is not implemented. `features/settings/repo/RepoActionsPage.tsx:191-194` uses the generic "Couldn't save the actions" from `save()`. Fix: use the named message for this switch, and test it.
- MUST Checklist item "Spotlight is available only when the repo setting is on and the workspace is local": the setting is checked (`spotlight.ts` `#start`), but nothing checks that the workspace is local (no cloud host is built, so this is cheap to state in one place). Fix: refuse a non-local workspace with a plain message, or move the item to the cloud plan and delete it from this issue.
- LATER `core/services/spotlight.ts:227-231`: starting stops every other active Spotlight, including those of other repositories, by calling `#stopWorkspace` outside that workspace's queue. Two starts for different repositories stop each other for no reason, and a stop already running for the other workspace can race the direct call (two restores at once). Fix: stop only workspaces with the same `rootPath` (`#roots` already holds it) and go through `this.stop(id)` so the keyed queue serialises it.
- LATER `core/services/spotlight.ts` `openRepoTerminal` and its failure log have no test (nothing fails if the repository terminal is never opened). "Quitting the app does not restore" has no test either. `container.app-01.test.ts:488` only spies on `healAfterCrash`.
- LATER `core/container.ts:1023-1024`: a failed start-up heal becomes a warning in a list. If the restore failed, the user's repository root still holds Spotlight's files and nothing says so. Surface it as a toast or a notification.
- LATER `core/services/spotlight.ts` `stopRuns` is optional and silently becomes "ok" when absent (`#stopRuns`), while the other three optional deps return an error. The container wires it; make it required.
- Specs and headers: "Built now … waits for the terminal service's 20 second watchdog, then restores the root" is not kept when the stop is unconfirmed (see above). Other header lines match the code. Duplication: none found.

## SET-13 Chosen program paths reach terminals and scripts

- MUST The chosen executable does not win in a login shell, so the feature does not do what its header says ("put first on PATH"). Checked on this Mac: `PATH="$dir:/usr/bin:/bin" /bin/zsh -l -c 'echo $PATH'` returns a PATH where `$dir` is the 19th entry, behind `~/.local/bin`, `/opt/homebrew/bin` and others. Interactive terminals start `zsh -l`, and scripts run as `login.shell -l -c` (`core/services/terminals.ts` runScript), so the user's own `claude` in `~/.local/bin` is found first. The Rust tests (`pty.rs`, `shell.rs` `set_13_*`) only read the env that is set before the shell starts. Fix: put the prefix back first after the profile runs (for example a small zsh/bash init that prepends `$CONDUCTED_PATH_PREFIX`, which belongs with RUN-09's shell integration), and add a test that runs a real login shell and checks `command -v claude`.
- MUST `core/services/system.ts:149-153`: a staging failure (`path_override_invalid`, the chosen file was deleted) is written to the log and the plain bundled folder is used. The terminal then runs a different `claude` than the one the user chose, with no message. This is a silent fallback (engineering.md "No silent failures"). It copies Conductor ("Failed to stage agent PATH override shims … fall back to the plain prefix", services-map 5A.8.2), so this is a conflict between D020 and the banned-pattern rule; the rule is the hard one. Fix: return the error, show it when a terminal or script opens ("Your chosen claude path can't be used: …"), and let the terminal still open with the plain folder only after the user has been told.
- MUST Two disagreeing "bundled bin folder" values. `src-tauri/src/binaries.rs:619-621` returns `app_data/bin` when nothing is chosen, while `core/services/system.ts:135` uses `binDir(paths)` (`resources/bin`) and never calls the command with an empty map, so the Rust branch is dead and wrong. Fix: delete the empty branch from the command (or make it the only source of the folder and remove the TS copy).
- MUST Duplicated logic: the block that reads `CONDUCTED_PATH_PREFIX` and writes `PATH` appears twice, `src-tauri/src/pty.rs` (build_command, near line 463) and `src-tauri/src/shell.rs:443-450`, differing only in the variable names. Fix: one helper in `shell.rs` that takes the env and the base PATH and returns the PATH.
- LATER `src-tauri/src/binaries.rs:656`: old shim folders are pruned only when something is chosen. Clearing both settings leaves the last `bin-overrides/<hash>` folder forever (the lifetime rule says what removes it; nothing does). Fix: prune with `keep = ""` in the empty case, after the dead branch is dealt with.
- LATER `core/services/system.ts:136-143`: the loop over `["claude","codex"]` checks `key === undefined` for a name that always has a key; the `Partial<Record<ManagedProgram, string>>` is built with a cast-free but pointless indirection. Cosmetic.
- LATER `src-tauri/src/binaries.rs` header says "a path that is missing or not executable (a named error, and no shim is written)", and that holds; a symlink to a directory, or a file that is executable but is not the agent, is accepted. No test for a directory path. Add one.
- LATER Tests: `run-scripts.set-13.test.ts`, `terminals.set-13.test.ts` and `system.set-13.test.ts` use injected `pathPrefixFor` functions; the join test (`s1-core-2.join.test.ts:463`) mocks `syncPathOverrides`. Nothing exercises the real Rust command from TypeScript besides the adapter test. Acceptable for now, but the shell-resolution test above is the one that would have failed.
- Checklist: all three items have code. "The bundled bin folder is put on PATH for scripts and terminals through one path prefix variable" works for run actions, setup and archive (`run-scripts.ts`), and for terminals.

## WS-11 Backlog workspaces: add now, start later

- MUST `app/CreateWorkspacePage.tsx:343-359`: when a backlog workspace is opened to start, the whole form stays editable (repository, "create from", prompt, model, plan mode, section), but `Start` calls `startFromBacklog(backlogEntry.id)`, which creates from the stored row. Anything the user changed is silently dropped. Fix: either lock the fields in start mode, or pass the edited input to `startFromBacklog` (and save it to the row first). Test: edit the prompt in start mode, press Start, and check the created workspace's first message.
- MUST `core/services/workspace.ts:2155-2158` (`startFromBacklog`): `create` runs first and the backlog row is deleted afterwards. If the delete fails, the workspace exists, the user sees "Couldn't start the workspace", the row stays, and a second Start makes a second workspace from the same draft. Fix: delete the row first and put it back (same id, same content) if `create` fails, or make the two steps one transaction; add a test with a failing delete.
- MUST Invented default: `app/CreateWorkspacePage.tsx:164` and `features/workspace/BacklogScreen.tsx:43` read `unstarted_workspaces_enabled`, a key that is not in `core/registries/settings.ts`, and treat "absent" as on. The comment says so. So the switch cannot be set, the "off" empty state and the hidden "Add to backlog" are unreachable in the app, and `WorkspaceService.addToBacklog` does not check the setting at all. The tests turn it on or off by seeding the store. Fix: add the setting to the registry with its Conductor default (or delete the gating and the "Backlog is turned off" screen), and check it in one place.
- MUST `core/services/workspace.ts:2139-2145` and `core/db`: "No ready repository. Pick one to start this workspace." can never be reached in the app. `backlog_workspaces.repo_id` is `ON DELETE CASCADE` (migration `0004`, line 82), so removing a repository deletes its drafts before Start can show the message. The unit test (`workspace.test.ts:985`) passes because it deletes the repo row from a fake. Also "Pick one" has no picker, and a repository that exists but is not ready (folder gone) is not checked. Fix: keep the drafts when the repository is removed (change the foreign key in a new migration, never edit 0004) and let the Backlog row offer a repository picker; or drop the cascade claim and say in the issue that the message is dead.
- MUST (lifetime) The cascade above also deletes the user's saved prompts without a word when a project is removed ("Nothing silently dropped"). Same fix as above, or a confirmation that names the drafts.
- LATER Deviation from Conductor, flagged by the header as a design choice: Conductor lists unstarted workspaces in the sidebar and offers Start in the sidebar's Workspace actions (ui-map 3.1, 3.8). Ours is a separate `/backlog` screen. The "Workspace actions: Start for unstarted workspaces" item is met only on that screen. Needs the owner's decision (D020/D022), not a code fix.
- LATER `core/status/workspace-status.ts:26-29` still says removing or producing the "unstarted" label "waits for WS-11". The label is now produced by `features/workspace/BacklogScreen.tsx:26` through `statusText`, but not by the shared status rule, so the sidebar and Home still never show it. Update that header line to say which it is.
- LATER Tests: `BacklogScreen.ws-11.test.tsx` covers list, start from row, start from menu, Cmd+Enter and remove. Header line "Must handle: loading, an empty backlog, a failed start (an error toast and the row stays)" has no test for loading, empty or the failed start. The backlog screen's selected row has only a text colour change (`aria-current:text-fg`), so the selection that Cmd+Enter acts on is hard to see.
- LATER `app/CreateWorkspacePage.tsx:313`: `makeInput` hard-codes `attachmentPaths: []`, so the backlog row's attachments are never filled by this page (attachments wait for COMP-07, as the header says). Fine now, but the checklist's "attachments" for backlog are carried only by the model.
- Duplication: none found. The `Start` button and the menu `Start` on each backlog row do the same thing; drop one if the owner agrees.

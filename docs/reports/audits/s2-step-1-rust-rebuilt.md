## PLAT-15 App menu with accelerators from the command registry

- MUST `apps/desktop/src-tauri/src/menu.rs:24-28` (header "a Help click emits the registry's command id so the command dispatcher can run it") and `:127` (`("app.openDiagnostics", "help.diagnostics")`). The registry (`apps/desktop/src/core/registries/commands.ts`) has no `app.openDiagnostics` (only `app.closeDiagnostics`, line 166). Clicking Help > Diagnostics emits an id that `dispatchCommand` rejects with "No command named app.openDiagnostics." (`command-dispatcher.ts:524`). A binding for it can never arrive either. Fix: add `app.openDiagnostics` to the registry under the feature that owns the Diagnostics page (APP-03), or drop the item and its alias until that feature exists. Header must name whichever is chosen.
- MUST `menu.rs:24-28`, `:129` (`app.openDebugTools`) and the issue item "open_devtools opens the web inspector from the Help menu". Rust has `window_toggle_inspector` (`lib.rs:254`), but no TypeScript code calls `platform.window.toggleInspector()` (grep: only `platform.ts`, `tauri.ts`, `memory.ts` and tests). `app.openDebugTools` (registry, feature APP-03) has no handler. The Debug menu item and Cmd+Alt+I therefore emit a command that does nothing in the live app. Fix: add a handler for `app.openDebugTools` that calls `toggleInspector`, or put the wiring on APP-03's checklist in `docs/plans/items/` as the engineering "Done means reachable" rule requires. I found no such checklist line.
- MUST `menu.rs:48-61` header "Menu accelerators come from the UI command registry" plus issue items "Cmd+Q quits and Cmd+, opens settings; both keys are fixed" and "Menu events carry the chosen command id to the UI". `plan_shortcuts` (`menu.rs:213-239`) accepts any accelerator for `app.quit`, `app.openSettings` and `tab.close`, so a `menu_set_shortcuts` call can rebind or clear the fixed keys. The UI today sends only the registry's own values (those commands are `configurable: false`), so nothing breaks now, but the Rust side states no rule and has no test for it. Fix: either refuse changes to fixed items in `plan_shortcuts` (report them in `rejected`) with a test, or cut "both keys are fixed" from any claim and keep it as a UI-only rule. LATER if the UI rule is judged enough; I rate it MUST only because the issue says "fixed".
- MUST `apps/desktop/src/platform/tauri.ts:1062-1067` (`createTauriMenu`): `setShortcuts` and `onCommand` still call `notImplemented("PLAT-33")`. This is tracked (PLAT-33 is blocked by PLAT-15 and PLAT-20, `docs/plans/backlog.md:47`), so it is not a hidden gap. But the issue items "Menu accelerators come from the UI command registry", "Menu bar accelerators ... are pushed to the Rust menu whenever bindings change" and "Menu events carry the chosen command id to the UI" are only true once PLAT-33 lands. Until then no accelerator reaches the menu in the real app and every menu click is lost. Surface it: keep PLAT-33 visible and make sure its row lists these three items.
- MUST `docs/plans/backlog.md:29` still says `stub` for PLAT-15 while `menu.rs` has no placeholder. `pnpm stubs` fails a `stub` row with no placeholders (engineering.md step 4). Set the row to `done`, or keep one named placeholder for the part not built (see the two items above).
- LATER `menu.rs:341-345`: `build_menu` uses `.expect(...)` on the state lock. A poisoned lock would panic at startup. `menu_set_shortcuts` returns an error for the same condition (`:407-410`). Use the same handling in both.
  Outcome: fixed already, 546507e2 `build_menu` and `menu_set_shortcuts` both recover a poisoned lock with `unwrap_or_else(|poisoned| poisoned.into_inner())` (`menu.rs:311, 433-437, 481-485`).
- LATER `lib.rs:301`: a menu routing failure is only `eprintln!`. Nobody sees it. Write it to the app log (`logger.rs`) so it reaches the diagnostics export.
  Outcome: open, item PLAT-15 (the handler still uses `eprintln!` at `lib.rs:722`)
- LATER `menu.rs:405-441`, `menu_set_shortcuts`: an error part-way leaves earlier items already changed, and the UI gets an error with no list of what applied. Two ids that map to one item in one call (for example `app.showShortcuts` and `help.keyboardShortcuts`) both report as applied, but only the last one wins. Plan the changes per menu item first and report duplicates as rejected.
  Outcome: open, item PLAT-15 (duplicates and fixed keys are now rejected in the pure `plan_shortcuts`, `menu.rs:254-292`, but applying the plan still mutates each item in turn and a later `set_accelerator` error returns without the applied list, `menu.rs:487-515`)
- LATER Behaviour check against `native-and-sidecar-map.md` A5: all items in the A5 table are present except the three left out on purpose (Best Practices, Submit a Prompt, Send Feedback). The omission is documented in the header. Settings/Quit/Debug accelerators match. View sidebar toggles have no Rust accelerator by default, which matches Conductor.
  Outcome: wrong, not a defect: the audit itself confirms every A5 item except the three documented omissions, and the header still records them (`menu.rs:33-42`).
- LATER Tests: `plat_15_the_custom_menu_items_are_present` and the routing tests exercise the real tables, and the `QuitGate` race test is real. Not tested, because they need a running Tauri app: `build_menu` (structure of the menu, Edit items kept), `handle_menu_event` emitting events, `menu_set_shortcuts` actually calling `set_accelerator`, `window_toggle_inspector`, and the release `devtools` feature (`Cargo.toml:23` has it, nothing proves it). ## PLAT-20 Attachments: copy dropped files, shrink large images

- MUST `apps/desktop/src/platform/tauri.ts:1081-1086` (`createTauriAttachments`): `materialize` and `resizeImage` still call `notImplemented("PLAT-33")`. Tracked under PLAT-33, but until it lands the two commands are reachable only from Rust tests. The issue items "A command materializes dropped or pasted attachments into files" and "Attachments can be added from a file picker ... and are copied into the app" are not live. Same fix as PLAT-15: keep PLAT-33 visible with these items.
- MUST `docs/plans/backlog.md:34`: PLAT-20 is still `stub` although `attachments.rs` has no placeholder. `pnpm stubs` fails this combination. Set to `done` (after the items below are settled).
- MUST `attachments.rs:241` and `:175-231`: `prepare_destination` creates the draft root and the destination parents before the source is checked. A missing source, a folder source or an oversized source leaves empty folders under `draft-attachments/`. `plat_20_materialize_refuses_a_missing_source` only asserts that the destination file does not exist. Header line "A failed copy removes its temp file" is kept, but the engineering rule "leave nothing behind" is not. Fix: check the source first (lines 243-263), then prepare the destination; add an assertion that the draft folder has no new entries after each refusal.
- MUST `attachments.rs:278-292`: the 4.5 MiB branch (`metadata.len() > MAX_IMAGE_BYTES`) has no test. Every resize test uses a pixel dimension over 7800. A test with a small-dimension, noisy image over 4.5 MiB would fail if the byte check were removed. Same for the issue item "Images are limited to 7800 px and 4.5 MiB". Add that test.
- MUST `attachments.rs:395-408` and the header line "If the image is still over `MAX_IMAGE_BYTES` after quality 0.7, fail with `attachment_too_large`": only `encode_jpeg_within_limit` is tested (with a limit of 0). No test drives `materialize_into` to this error, and none checks that a failed resize leaves no destination and no temp file. Add one end-to-end case (a large noisy image at the limit).
- MUST `attachments.rs:281`: with `resize_image: true`, an animated GIF that is over the limit is copied unchanged, and with `resize_image: false` an oversized image is also copied unchanged. The issue says "Images larger than 5 MB are refused with an Image too large banner" and "Images over 5 MB fail to attach". Nothing in Rust refuses an image over 5 MB (only sources over 200 MiB, line 259), and I found no UI code for the banner (COMP-07 is still a stub, so this may belong there). Decide where the 5 MB refusal lives and write it on the owning feature's checklist. If it belongs here, add it with a test. As it stands the issue's three 5 MB items have no code and no test in PLAT-20.
- MUST `attachments.rs:298`: `is_image: !image.animated`. The doc comment on `MaterializedAttachment.is_image` (line 73) says "a still image the app can show", which matches, but the header says only "A file named `.png` that is not an image ... `is_image: false`". An animated GIF is an image, copied as is, and reported `is_image: false`. The test `plat_20_materialize_copies_an_animated_gif_as_is` never asserts `is_image`. Either assert the behaviour and state it in the header, or report `true`. Pick one and test it.
- LATER `attachments.rs:240`: `path` returns the requested destination, not the canonical `target`. When the app data folder sits behind a symlink the UI gets a different spelling than the file's real path. Return the path actually written, or say in the header why the requested one is returned.
  Outcome: open, item PLAT-20 (`materialize_into` still returns `reported_path` from `destination`, `attachments.rs:267, 298`)
- LATER `attachments.rs:341-348`, `:307-321`: the probe reads only dimensions, but `resize_image_bytes` decodes the full pixel buffer. A highly compressed 60,000 x 60,000 PNG under 200 MiB would allocate far more memory than the header's "memory use is bounded" claim implies. The `image` crate's default limits may stop it, but no test shows it. Check the dimensions from `probe_image` against a pixel-count cap before decoding, and test it.
  Outcome: open, item PLAT-20 (`probe_image` returns dimensions at `attachments.rs:403-417`; `resize_image_bytes` decodes at `:443` with no pixel-count check before it)
- LATER `attachments.rs:324-338`: `gif_is_animated` decodes two full frames of every GIF, including 8000-wide ones, only to count frames. It is correct but heavy. Fine for now.
  Outcome: wrong, not a defect: the audit accepts the cost ("Fine for now") and the code is unchanged (`attachments.rs:420-434`).
- LATER `attachments.rs:427-437`, `:562-567`: `remove_temp` and the test `Drop` only `eprintln!` when cleanup fails. The first hides a leftover file from the user; use the app log. The test cleanup failing silently can hide the "run leaves nothing behind" guard failing.

This is one function called twice, so it is not duplicated logic, but the test `plat_20_image_resize_shrinks_a_large_image` calls `materialize_into` directly and so never exercises the `image_resize` command. It duplicates `plat_20_materialize_shrinks_a_large_image_to_the_pixel_limit`. Remove it or test the command body.
  Outcome: open, item PLAT-20 (`plat_20_image_resize_shrinks_a_large_image` still calls `materialize_into` directly, `attachments.rs:974-997`)

- LATER: the instruction wording differs from Conductor's one-liner ("Commit and push all changes", services-map 3.5). The header says wording is our own. Fine, but the commit instruction does not say "all changes" explicitly in the test. Low risk.

Pull's hand-off is the same "reconcile" request, but it never reads the repo prompt, so a repo prompt applies to one and not the other. Either confirm that reconcile has no custom prompt (the Prompts page has none) and remove `customPrompt` from `reconcileInstruction` (agent-instructions.ts:186-218, with its "Repository instructions for Reconcile" branch, which no caller can reach), or wire it. Same rule as GIT-05's finding.
- MUST: duplicated logic, `git.ts:1084` / `1085` (`pullStrategy(rebase.value, ff.value)`, which reads `pull.rebase` through `stdout`) and `git.ts:1191-1206` (`#pullRebaseStrategy`, which reads `pull.rebase` through `run` and checks exit codes by hand). - MUST: duplicated logic, `pullUsesRebase` (git.ts:161-163) wraps `pullRebaseStrategy` (agent-instructions.ts:104-108), which wraps `REBASE_PULL_VALUES`. `PullStrategy` (git.ts) and the `"rebase" | "merge"` union in agent-instructions.ts are the same idea in two files, and `agentStrategy` (git.ts:1085) converts between them. - MUST: header claim, `git.ts` header: "a dirty or diverged tree goes to the agent". With `pull.ff = only` and a diverged tree the code does not go to the agent, it runs `merge --ff-only` and returns git's error (git.ts:1113-1121). ## GIT-07 Resolve conflicts, done by the agent on request

- MUST: `container.ts:400-410`: `promptFor` is never passed to `new GitService({...})`. The `GitServiceDeps.promptFor` (git.ts:386) is optional, so `resolveConflicts` always takes the `ok(null)` branch in the app. The checklist item "A repo-level custom prompt replaces the default text for Resolve conflicts" works only in the unit test, which supplies its own `promptFor`. The git.ts header claims "a resolve-conflicts request uses the repository prompt when it has one". `repo.ts:375` and `:897` already load `prompts.resolveConflicts`. Fix: pass `promptFor` from the repo service in `container.ts`, make it required (no silent `undefined` branch at git.ts:1167-1169), and add a container-level test.
- MUST: header claim, `agent-instructions.ts` header says Resolve conflicts "replaces" the built-in text but also that "the Resolve conflicts request names the target and the rebase or merge steps". With a custom prompt, the text names neither the branch nor the target (agent-instructions.ts:120-121 returns `custom` at once). This matches Conductor's replace semantics, so the second claim should read "when no repo prompt is set".
- MUST: `agent-instructions.ts:115-147` and `:186-218`: `resolveConflictsInstruction` and `reconcileInstruction` build the same rebase and merge steps with the same wording ("Rebase this branch onto", "Update the remote branch with `git push --force-with-lease`...", "Push the branch with `git push`"). Duplicated logic inside the batch. Fix: one `rebaseOrMergeSteps({strategy, remote, remoteTarget})` used by both.
- MUST: checklist "When the branch has diverged from its target, rebase or merge is chosen by pull.rebase and the agent does it." The Resolve conflicts button (`git.ts:1161`) does not check divergence. That is correct (the button shows only when the header says conflicts), but no test shows that the header offers "resolve" only for a conflicted PR. The git-header tests are outside this batch; add one on the `resolve` action to make the item testable.
- LATER: `agent-instructions.git-07.test.ts:58` repeats the list of accepted `pull.rebase` values as a table. Git itself accepts only `true`, `false`, `merges`, `interactive`; `yes`, `on`, `1`, `preserve` are boolean aliases or older values. Matches services-map 3.6.4, keep.
- LATER: `git.git-07.test.ts` has `makeService` with a hand-cast set of deps. Prefer `createTestContainer`, as `engineering.md` asks.
- LATER: a rebase of a pushed branch ends with `--force-with-lease`. The header of `git.ts` says the app never force-pushes. That is true (the agent pushes), but say so in the header.

## SIDE-20 Tell the app when the agent changes a chat's mode

- MUST: three checklist items are not built and not moved. `packages/protocol/src/rpc.ts:402` adds a separate `agentConfigChanged` notification. The items ask for (a) the live-state notification to carry the updated config, (b) the session-event notification to carry "index, new events, updated state and updated config", and (c) an `enterPlanModeNotification` and an `onEnterPlanMode` callback. The code has `onConfigChanged` (`runner.ts:75`) and a single new notification, and `liveState` (rpc.ts:392) and `sessionEvent` are unchanged. Neither `rpc.ts` nor `manager.ts` marks this as "Our design choice". Fix: either add the design-choice note and rewrite the four items in `docs/plans/items/system.tsv` (lines 203, 207, 476, 542) to match, or build them.
- MUST: `handlers.ts:183-188`: when the config write fails, the handler throws and the tunnel only logs it (header lines 14-15). The rule in engineering.md refuses "an error that is only logged". The user's chat then shows a mode that differs from the agent's real mode (plan mode on or off), and nobody hears of it. Fix: surface it to the user (toast or chat error) and keep the previous config marked stale, or retry through the same single writer.
- MUST: `claude-session.ts:650-657` (`applyPermissionMode`): `changePlanMode(false)` runs on every non-plan mode, including the sync before each turn (`syncLiveConfig`, line 632). It is guarded by `this.config.planMode`, so it only fires when the config still says plan. But it is also called when the user turns plan mode off in the app: `this.config` is already `planMode: false` there, so nothing is sent. The one case it fires is an approved plan, as designed. The comment on line 646-649 says "Leaving plan mode here is a change the agent made". Add a test for the user path (app turns plan off, sidecar sends no `agentConfigChanged`), because nothing proves that today.
- MUST: `claude-session.ts:481-502` (`notePlanMode`): an init message with `permissionMode === "plan"` sets `appliedPermissionMode = "plan"` and notifies, even when the app has just asked for a non-plan mode and `syncLiveConfig` has not run yet. Then the app's own choice is overwritten by the CLI's stale mode. No test covers an init reporting `plan` after the user turned plan off. Add one, and decide which side wins.
- MUST: no test for the `exit plan then agent re-enters in the same turn` order, and none for two `agentConfigChanged` notifications arriving out of order. `sessions.chat-02.test.ts:619` covers two overlapping `applyAgentConfig` writes in the service. The tunnel and `handlers.ts` keep no order guard, so the service's keyed queue is the only protection, and a user-made config write (`#setConfig` from the composer) does not go through `#agentConfigWrites`. Check that a composer change cannot be overwritten by an older agent notification; add a test.
- MUST: header claim, `manager.ts` Must handle: "a config the agent changes by itself (plan mode) updates the chat's state". The code updates `state.config` and `state.agentConfig` (manager.ts:838-846). The test (`manager.test.ts:1000-1030`) only checks the notification content; it never reads `state.config` back. Add an assertion that the next `sendMessage` without a config uses the new mode.
- LATER: `packages/protocol` has no schema test for `agentConfigChanged` (the reason enum). Add one in `events.test.ts` style.
- LATER: only the Claude runner implements `onConfigChanged`. Codex and the ACP runners never tell the app when they change mode. The checklist lists "Callback onEnterPlanMode ... (other-runners 1)". Say in the issue that other runners are not covered.
- LATER: `handlers.side-20.test.ts` builds ports with a cast (`overrides as unknown as SidecarHandlerPorts`). Fine for a handler, but nothing tests the real wiring `container.ts:212` to `sessions.applyAgentConfig` end to end.
- LATER: backlog rows for GIT-05, GIT-06, GIT-07 and SIDE-20 are still `stub` (docs/plans/backlog.md lines 75, 238-240). The issues ask to set `done` in the closing PR; `pnpm stubs` will need it once the MUST items above are fixed.

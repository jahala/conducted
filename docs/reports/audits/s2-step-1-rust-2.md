# Audit: batch n8-s1-rust-2 (PLAT-29, PLAT-32, PLAT-34)

Read-only audit of branch slice2/step-1 at 39b1a7c. CI-catchable failures were skipped. Nothing was run; every claim below comes from reading the code, the issues and the research.

## PLAT-29 Limit the paths, programs and links the webview can reach

- **MUST** `apps/desktop/src-tauri/src/shell.rs:1007` (`check_program_allowed`): only the file name is compared, so any path whose last part is an allowed name passes. `/tmp/x/git` runs. The window can create such a file: `cp` is on the list and keeps the executable bit (`cp -p /usr/bin/curl <temp>/git`), and the temp folder is a file root. The "named scope" is therefore bypassed. Fix: for a path with a directory part, require the resolved path to sit in an allowed folder (system bin folders, the app's `bin/`, the managed agent-binaries folder). For a bare name, resolve it on PATH and apply the same folder check.
- **MUST** `apps/desktop/src-tauri/src/pty.rs:407`: `pty_spawn` with `command` builds `CommandBuilder::new(&command.program)` with no call to `check_program_allowed`. A program outside the list starts through the terminal command. The `shell.rs` header (line 36) claims the program limit for `shell_run` and `shell_start` only, so the header is true. The checklist item "Shell access is limited to named scopes; ours runs any program" is still open for this path. Fix: call the check in `pty_spawn` for `command.program`, or write down in the header and the issue that the terminal is out of scope and why.
- **MUST** `apps/desktop/src-tauri/src/files.rs:41-43` and `apps/desktop/src/core/services/repo.ts:433`, `workspace.ts:414-483`, `file-diff.ts:96`, `git/worktree.ts:281`: the path scope allows `~/conducted`, the app folders and the Claude config files. The UI also calls `fs.stat`, `readText`, `mkdirp`, `readDir` on the repo folder the user picks (any path), on `.conducted/settings.toml` inside it and on its `.git` exclude file. All of these now fail with `fs_out_of_scope` for a repo outside `~/conducted`, which is the normal case. The header admits "no command registers" extra roots. This is a placeholder-shaped gap: the feature is marked done and the main flow (add a repo) breaks. Fix: add a command (for example `fs_register_root`) that the repo and workspace services call when a repo is added or opened, stored in managed state and merged in `allowed_roots`. Add a test that a registered root is reachable and an unregistered one is not. Alternatively add the repo folders to the roots from the database at startup.
- **MUST** `apps/desktop/src-tauri/capabilities/default.json:10-11`: the opener allows `https://*` and `http://*`, so any host opens. The issue item and the research (A3) say the opener is limited to hosts (conductor.build, github.com/user-attachments, api.github.com and so on) plus IDE schemes. The file header (line 47) says "web, mail, telephone and the IDE and chat schemes", which hides this as if it were the rule. `mailto:` and `tel:` are not in the research either. Fix: either list the hosts from A3, or add an "Our design choice:" line saying all web links open because chat shows arbitrary links, and update the issue text. Also drop `mailto:` and `tel:` or justify them.
- **MUST** `apps/desktop/src-tauri/src/files.rs:589-592` (`checked_target`): `check_path_in_scope` resolves the path, but the commands then act on the unresolved path (`checked_target` returns `absolute_path(path)`). A link inside a root can be swapped to point outside between the check and the use. This is a check-then-use gap on a security check. Fix: act on the resolved path that `check_path_in_scope` returns (for `fs_stat` keep `symlink_metadata` on the link itself, so resolve only the parent), or open the file once and check the handle.
- **LATER** `apps/desktop/src-tauri/src/shell.rs:977-1003` (`ALLOWED_PROGRAMS`): the list holds `sh`, `bash`, `zsh`, `cp`, `open`, `git`. Each of these reaches any path or any program (`bash -c`, `cp a b`, `open <url>` bypasses the opener scope). The research also lists bash and open, so this matches Conductor, but the header and `default.json` description imply a boundary. Say in the header that the list narrows accidents and is not a sandbox, or restrict arguments for `open`, `cp` and the shells.
Outcome: fixed already, 34a965d8 `shell.rs` now has "Our design choice: `ALLOWED_PROGRAMS` narrows accidents; it is not a sandbox" and says the working folder is not limited (`shell.rs:53-57`).
- **LATER** `apps/desktop/src-tauri/src/shell.rs:981-985`: `sleep`, `echo`, `true` are in the production list for the platform contract test (`platform/contract.ts` uses `/bin/echo`, `/bin/sleep`). `true` has no caller at all. Keep the production list to programs the UI runs; let the contract pass its own list through the `allowed` parameter, or use the shell for those cases.
Outcome: open, item PLAT-29 - `sleep`, `echo` and `true` are still in `ALLOWED_PROGRAMS` (`shell.rs:1147-1149`).
- **LATER** `apps/desktop/src-tauri/src/files.rs:1127-1298` (tests): the scope tests cover read, `check_path_in_scope`, `..`, links and prefix siblings. Nothing proves that `fs_write_text_atomic`, `fs_mkdirp`, `fs_read_dir`, `fs_stat` and `fs_trash` refuse an outside path. Delete the `checked_target` call from one of them and no test fails. Add one outside-root test per command.
Outcome: fixed already, 34a965d8 `plat_29_every_file_command_refuses_an_outside_path` now covers write, stat, mkdir, read-dir and trash (`files.rs:1407-1451`).
- **LATER** `apps/desktop/src-tauri/src/files.rs:1268-1298`: the capabilities test checks that strings occur in the JSON file. It does not prove that a URL is refused or allowed, and it would pass with `https://*` replaced by anything containing the same text. A stronger test would parse the JSON and assert the exact list of scopes and the absence of `shell:*`, `fs:*`, `opener:default`.
Outcome: fixed already, 55724de8 the test parses the JSON and asserts the exact opener list and the absent broad defaults (`files.rs:1608-1649`).
- **LATER** `apps/desktop/src-tauri/capabilities/default.json`: the research lists the System Settings Full Disk Access link in the opener scope (A3). It is missing. PLAT-24 probably needs it; add it there or here.
Outcome: fixed already, 34a965d8 `x-apple.systempreferences:*` is in the opener scope (`capabilities/default.json:18`).
- **LATER** `apps/desktop/src-tauri/src/lib.rs:251-252`: `tauri_plugin_shell` and `tauri_plugin_fs` stay registered though nothing grants them. They are dead weight and a future grant would silently widen the scope. Remove both plugins and the Cargo lines, or note why they stay.
Outcome: open, item PLAT-29 - both plugins are still registered (`lib.rs:694-695`).
- **LATER** `apps/desktop/src-tauri/capabilities/default.json:25-26`: `sql:default` plus `sql:allow-execute` let the window open and write any database the plugin can load. Not verified whether the plugin accepts an absolute path. Check, and scope it to `sqlite:conducted.db` if it does.
Outcome: open, item PLAT-29 - `sql:default` and `sql:allow-execute` are still granted without a path scope (`capabilities/default.json:23-24`).
- **LATER** `apps/desktop/src-tauri/src/files.rs:232-239`: the whole temp folder and the whole app data folder are roots. The research names only the Claude files; the extra roots are not listed under "Our design choice". Add that line.
Outcome: fixed already, 34a965d8 the header now records the extra roots as a design choice (`files.rs:53-57`).
- **LATER** `apps/desktop/src-tauri/src/shell.rs`: `cwd` of `shell_run` and `shell_start` is not scoped. A program on the list runs in any folder. Same fix as the program check, or note it.
Outcome: fixed already, 34a965d8 the header now states that the working folder is not limited (`shell.rs:55-56`).
- Header check: the `files.rs` header keeps its claims except the scope paragraph, where "the `fs_*` commands use `allowed_roots` until the UI registers its workspaces" holds, but see the third MUST. `shell.rs` header claims are kept.

## PLAT-34 Check the bundled helper programs at launch

- **MUST** `apps/desktop/src-tauri/src/lib.rs:272-325`: `binaries::programs_verification_errors` is not in `generate_handler!`. The UI call `programs.verificationErrors()` (`platform/tauri.ts:985`) fails with a "command not found" error in the real app. The Rust command exists and is untested through Tauri. Fix: add `binaries::programs_verification_errors` to the handler list, and add a test that every `COMMANDS` name in `tauri.ts` appears in `generate_handler!` (a guard, since the same gap can hit every command).
- **MUST** `apps/desktop/src-tauri/src/binaries.rs:167` (`emit_verification_errors`) is called by nothing, and `lib.rs:267-271` (`setup`) does not start the check. The issue item "Launch verification copies bin, runs each program and re-copies on failure" and "binary_verification_errors event reports ..." have no live path: nothing runs at launch and nothing emits the event. Fix: start the check from `setup` on a background thread, keep the result in managed state (research A2: "state read through get_binary_verification_errors"), emit the event when done, and let the command read the state.
- **MUST** `apps/desktop/src-tauri/src/binaries.rs:177-180`: the command re-runs the whole copy and the `--version` runs on every call, instead of reading the launch result. The command is synchronous, so it blocks the main thread for up to 4 programs x 2 runs x 5 s = 40 s. Two overlapping calls (or a call during the launch check) copy into the same files at once. Fix: store the launch result in `State`, return it from the command, and run the check once under a single-flight guard on a worker thread.
- **MUST** no UI listener: `platform.ts:409` has `verificationErrors()` only. The event `programs://verification-errors` (`tauri.ts:312`) has no `onVerificationErrors` in the `Programs` interface, no `listen` and no consumer, and `verificationErrors()` has no caller outside tests (grep of `apps/desktop/src`). The "event reports ..." checklist item is therefore not met, and `plat_34_the_event_name_is_the_one_the_platform_listens_for` (line 529) asserts a constant against itself, because nothing listens. Fix: add the listener to the Platform interface and the Tauri and memory implementations, with a dispose, and test the event with a real emit; delete the constant test.
- **MUST** `apps/desktop/src-tauri/src/binaries.rs:134-135` (doc comment of `verify_bundled_programs`): "returned in the list, newest run first". The code returns `ManagedProgram::ALL` order. Remove the claim.
- **MUST** header line "a destination that already holds the files (the copy replaces them)" (`binaries.rs:~48`): no test seeds a destination with a stale file and checks that it is replaced. `plat_34_recopies_a_failing_program_and_runs_it_again` does not cover it either, because the destination is empty at the first copy. Add the test. Also, `fs::copy` onto a program that is running (an agent started earlier) can fail with "text file busy" on macOS; the header should say how that is handled, and the test should cover it.
- **MUST** `apps/desktop/src-tauri/src/binaries.rs:228-264` (`run_program_with_timeout`) duplicates the run-with-timeout-and-kill logic in `shell.rs` (`shell_run` timeout and `process_group` kill). It also kills only the direct child, so a program that forks (a wrapper script) leaves its children running. The test uses `exec sleep`, which hides this. Fix: reuse the shell run path or `process_group`, and add a test with a script that does not `exec`.
- **LATER** `apps/desktop/src-tauri/src/binaries.rs:182-211` (`copy_bin_folder`, `copy_entry`): `fs::metadata` follows symlinks, so a link loop in `bin/` recurses until the stack ends. Research A9 says `bin/` holds symlinks for claude and codex. Use `symlink_metadata` and copy links as links, with a test.
Outcome: open, item PLAT-34 - `copy_entry` still calls `fs::metadata` and recurses through a directory link (`binaries.rs:432-445`).
- **LATER** `apps/desktop/src-tauri/src/binaries.rs:111-113`: if the re-copy of one program fails, `copy_entry(&from, &to)?` returns the error and drops the failures already collected for other programs. Collect the copy error as that program's `VerificationError` and go on.
Outcome: open, item PLAT-34 - the copy still propagates its error with `?` and discards the collected failures (`binaries.rs:252`).
- **LATER** `apps/desktop/src-tauri/src/binaries.rs:1-30` vs issue: the research A9 also strips quarantine, tracks source markers (size and time per file) so a re-copy only happens on a change, and removes unknown binaries from `bin/`. None of this is built, and the PLAT-34 header does not say so. The header says the copy replaces files on every launch, which with 308 MB of binaries is slow. Add an "Our design choice:" line, or build the markers.
Outcome: fixed already, 34a965d8 the header now records that the markers, quarantine strip and unknown-file removal are not built yet (`binaries.rs:122-124`).
- **LATER** `apps/desktop/src-tauri/src/binaries.rs:55`: the header calls the four programs "managed programs" and the issue says "agent programs". `ManagedProgram` has `gh` and `watchexec` (helpers) next to `claude` and `codex`. The names are fine; align the issue text.
Outcome: stale, only the issue's wording; the code keeps `ManagedProgram` and the header already says which entries are agent programs (`binaries.rs:194-196`).
- **LATER** name drift: the research and the issue say `get_binary_verification_errors` and `binary_verification_errors`; the code uses `programs_verification_errors` and `programs://verification-errors`. `docs/plans/tauri-commands.md:72` records the new names, so this is consistent with the docs. Note it under "Our design choice:" in the header so the audit trail is clear.
Outcome: fixed already, 34a965d8 the header records the name difference and points at `docs/plans/tauri-commands.md` (`binaries.rs:125-127`).
- Checklist vs tests: copy (tested), run each (tested), re-copy on failure (tested), still failing is reported (tested), cannot start (tested), timeout (tested), missing bundle (tested), copy error (tested). The command and the event have no test that would fail when the wiring is missing (see MUST items). The TypeScript test `tauri.verification.test.ts` uses an invoke stub, so it passes while the Rust command is unregistered.

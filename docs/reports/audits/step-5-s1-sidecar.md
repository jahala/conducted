# Audit: batch n5-s1-sidecar (SIDE-04, SIDE-05, SIDE-11)

Audited the committed branch `overnight/step-5` (files under `packages/sidecar/src/session/`, plus the call sites in `manager.ts`, `modes/sidecar-mode.ts` and `rpc/handlers.ts`). No test was run.

## SIDE-04 Turn lifecycle and stale-run guard

- LATER `packages/sidecar/src/session/turn.ts:147-163`: `cancel()` before `start()` (`run === null`) goes straight to `finish`, which takes an end checkpoint with no start checkpoint and publishes `turn_ended` for a turn that never began. Fix: return early when `run === null`, or document that the manager never does this and add a test.
  Outcome: open, item SIDE-04. cancel() has no `run === null` early return: it sets cancelling, skips invalidate, calls agent.cancel() and then finish({kind:"cancelled"}) (turn.ts:151-167), so a pre-start cancel still takes an end checkpoint and publishes turn_ended.
- LATER `packages/sidecar/src/session/turn.ts:227-229` (and `launch`, line 203-205): a run that went stale without `cancelling` (the manager called `runGuard.invalidate()` directly at `manager.ts:367` and `:476`) only calls `settle`. It publishes no `turn_ended` and no idle. This is fine if `liveState.drop` follows in those paths, but nothing in `turn.test.ts` proves it. Fix: add a manager-level test that a reset or shutdown mid-turn leaves no chat stuck on `working`.
  Outcome: fixed already, 90288d42. manager.test.ts now covers shutdown mid-turn (:1383-1428, including "takes no end checkpoint and writes no turn_ended") and resetAgent (:880-887), both asserting the chat is forgotten, not left working.
- LATER `packages/sidecar/src/session/turn.ts:183-192` and `:308-317`: `markWorking` and `updateLive` are the same try/catch-and-warn wrapper around `liveState.update`. Fix: have `markWorking` call `updateLive(beginTurn)`.
  Outcome: open, item SIDE-04. markWorking (turn.ts:187-196) and updateLive (:318-327) still repeat the same try/catch-and-warn wrapper around liveState.update.
- LATER `packages/sidecar/src/session/turn.ts:101-110`: a cancel writes `error: "aborted by user"` into the live state. This matches research (sessions.md line 73), but the SIDE-04 issue says "cancel gives idle". The file header never states the cancel error text. Fix: add the error text to the header's Must-handle list so the issue and code agree.
  Outcome: open, item SIDE-04. CANCELLED_BY_USER is still "aborted by user" (live-state.ts:57) and cancel writes it, but turn.ts's header Must-handle list (lines 6-20) never mentions the cancel error text.
- LATER `packages/sidecar/src/session/turn.ts:11`: the header says the turn waits for the previous turn's end checkpoint. That wait is not in this file, so it lives in `manager.ts` or nowhere. Fix: check where it is enforced and move the claim to that file, or add the wait and a test.
  Outcome: open, item SIDE-04. turn.ts:11 still claims the wait, but turn.ts contains no wait on a previous turn; the manager serialises turns instead.
- LATER (checklist) "Set chat status with a compare-and-set; an older write is dropped": the epoch check in `LiveStateStore.apply` covers `drop()` only. Late writes from a stale turn are blocked by the `isCurrent` checks in `Turn`, not at the store. This is fine, but no test names the compare-and-set claim. Fix: reword the checklist item or add a store-level test.
  Outcome: open, item SIDE-04. live-state.test.ts:294-313 covers drop and a late update after it, but no test names the compare-and-set claim for two overlapping updates.
- Tests: `run-guard.test.ts` and `turn.test.ts` cover order, the late-result drop, cancel during the start checkpoint, a rejecting runner and `beforeFirstWrite`. Items with no test: "Step 1: an abort controller per query; cancel aborts a query still in setup" (the code is in `manager.ts` `state.setup?.abort()`, no test in this batch's files), and "A host turn failure sets liveState.error; the cloud out-of-memory message rewrite" (cloud only, correctly deferred).

## SIDE-05 Event batching and live-state notifications

- MUST `packages/sidecar/src/session/event-batcher.ts:223,271` and `modes/sidecar-mode.ts:528-534`: `onWriteFailure` has no subscriber outside the test, so the header claim "surface the error after the last delay as a turn error instead of dropping events" is false in the running sidecar. After 6 failures the batcher only logs and retries forever; the chat never shows an error. Fix: in `sidecar-mode.ts` (or the manager), subscribe and set `liveState.error` on that chat, with a wiring test that fails if the subscription is removed.
- MUST `packages/sidecar/src/session/live-state.ts:85` and `turn.ts:291-294`: `setWaitingSince` has no non-test caller. `onBackgroundTasks` passes only `tasks`, so `waitingSince` is never set in production. Checklist items "Running tool ids and blocking TaskOutput waits are tracked and set waitingSince" and "Live state extra: waitingSince" are therefore not delivered (the research, claude-runner.md line 106, passes `waitingSince` with the background tasks). The reducer and its test exist, but the feature has no source. Fix: add a `waitingSince` field to the runner callback, wire it through `Turn.callbacks` to `setWaitingSince`, and add a test from callback to notification. Or move the item back to `scaffold: missing` in the backlog and say so in the header.
- LATER `packages/sidecar/src/session/event-batcher.ts:414-416`: the header and the checklist say events are "sent in batches", but `send` emits one `sessionEvent` notification per envelope. Batches only group the outbox append. The header's own "Our design choice" note covers the retry table, not this. Fix: state in the header that a batch is a write unit, not a wire unit.
  Outcome: fixed already, 9bc7e9f2. The header now says "Our design choice: a batch is a write unit, not a wire unit. It groups one append to the outbox" (event-batcher.ts:24-25).
- LATER `packages/sidecar/src/session/event-batcher.ts:23` and `event-batcher.test.ts:173`: the header and test name say `takeBatch`; the export is `takeBatches`. Fix: align the names.
  Outcome: fixed already, 9bc7e9f2. The export and the header and test names now all say takeBatches (event-batcher.ts:23, :59; test :141).
- LATER `packages/sidecar/src/session/event-batcher.ts:154-176`: the `minimalEvent` fallback (the last-resort shape-only event) and the `user_message`, `checkpoint` and `turn_ended` branches have no test. Only the `agent` case is exercised (`event-batcher.test.ts:317`). Fix: add a case where even the shrunk event exceeds the limit.
  Outcome: open, item SIDE-05. event-batcher.test.ts now exercises user_message, checkpoint and turn_ended (:265-353), but no test forces the minimalEvent last-resort branch (no "minimal"/"exceeds" test exists).
- LATER `packages/sidecar/src/session/event-batcher.ts:49-51`: `eventBytes` is a one-line alias of `jsonBytes`. Fix: use `jsonBytes` directly.
  Outcome: fixed already, 9bc7e9f2. eventBytes is gone; the batcher calls jsonBytes directly (event-batcher.ts:47, :128, :186-211).
- LATER `packages/sidecar/src/session/event-batcher.ts:390-411`: `appendBatch` retries without limit and keeps order, but there is no cap on queue growth while stuck (`chat.events` is unbounded). Fix: state the bound in the header, or surface backpressure.
  Outcome: open, item SIDE-05. appendBatch still loops `while (true)` retrying forever (event-batcher.ts:380-411), and neither the header nor the class caps `chat.events`.
- LATER (checklist) "Table session_state / session_live_state": `LiveStateStore` is in memory only. The table is app-side (DATA-01), so this is correct. The checklist item is not covered by any sidecar test. Fix: mark it as owned by DATA-01 in the issue.
  Outcome: wrong. The map already assigns session_live_state to DATA-01 (items/system.tsv:1089) and marks the SIDE-05 session_state row covered (items/system.tsv:817), so the checklist item is owned and covered.
- Tests: a real test exists for the 50/50/20 split, the byte limit, write-before-send, single flight, flush ordering, the retry table, the 60-second warning, the missing app, head and tail shrinking, flush-before-publish, idle after the last event, ordered updates, and no index on live-state notifications. Items with no test: "Send retries" is tested only against the outbox append (as designed), and "A runner callback becomes an agent event with the message, user message id and turn id" is covered only in `turn.test.ts`.

## SIDE-11 Interactions

- MUST `packages/sidecar/src/session/interactions.ts:14-18` and `:226-242`: the header says a disconnected app makes "a question or approval resolve as withdrawn" and adds "Conductor does the same for the first two". The research says plans are rejected and questions get empty answers (sessions.md line 141, claude-runner.md line 251). `unavailableAnswer` returns `{ kind: "withdrawn" }` for `question`, so the claim is false and the behaviour differs from the spec in the issue ("questions get empty answers"). Fix: return an empty `question` answer for `question`, keep `withdrawn` for `tool_approval`, and correct the header. Add a test that asserts the question answer.
- MUST `packages/sidecar/src/session/interactions.ts:203-217` duplicates `packages/sidecar/src/session/live-state.ts:129-142`: `publishLive` builds a second per-chat promise chain to keep updates in call order, but `LiveStateStore.update` already chains per chat, in call order. Fix: call `this.deps.liveState.update(...)` directly and keep only the `.catch` logging.
- MUST (checklist) "Cancelling a plan review denies with the text Plan not approved": no non-test code and no test in `packages/sidecar` contains this text. A cancel resolves the plan as `{ kind: "withdrawn" }`, and nothing in this batch maps that to a denial with the text. Fix: do the mapping where the Claude permission handler receives `withdrawn` for `plan_approval`, and test it. Or record the item as not done in the backlog.
- LATER (checklist) "answerUserQuestion carries a snapshot ... replies ok, superseded or sessionGone": `answer()` and `manager.answerInteraction` return only `{ accepted, superseded }`. An unknown chat is reported as `superseded: true`, and no `sessionGone` exists. Staleness is detected by `interactionId`, which is a sound replacement. Fix: say so in the header as a design choice.
  Outcome: fixed already, 9bc7e9f2. The header now records the design choice: an unknown answer is reported by interaction id as superseded, with no separate sessionGone reply (interactions.ts:34-36).
- LATER (checklist) "Live state extra: activeQuestions / activeUserInteraction": both are folded into one `openInteraction`, and queued interactions are not visible to the UI. Fix: note this in the header, since the UI can only show the open one.
  Outcome: fixed already, 9bc7e9f2. The header now states that only the one open interaction is published and that activeQuestions and activeUserInteraction fold into openInteraction (interactions.ts:37-39).
- LATER `packages/sidecar/src/session/interactions.test.ts:162`: the first test lacks the `SIDE-11` prefix the other tests use. Fix: rename.
  Outcome: fixed already, 9bc7e9f2. Every test in interactions.test.ts now starts with "SIDE-11", including the first (:102) and the one at :160.
- LATER (checklist) "After a steer / a new message: the open interaction is cancelled": `withdrawAll` is called at `manager.ts:295,372,475,569,664,746`, but this batch's `interactions.test.ts` tests only the broker, not that a new message or a steer calls it. Fix: confirm `manager.test.ts` has a test for each call site (not verified here).
  Outcome: open, item SIDE-11. manager.test.ts proves withdrawAll on cancel only (:826); no test covers the new-message, steer, resetAgent or shutdown call sites.
- Tests: a real test exists for one open per chat, the queue, answering a withdrawn interaction (superseded), a wrong-kind answer, a disconnected app, a thrown request, resend on reconnect, Codex expiry, and independence across chats. No test: the plan-denial text, the empty question answer, and `manager.onAppAttached`.

Summary: SIDE-04 6 findings (0 MUST, 6 LATER); SIDE-05 8 findings (2 MUST, 6 LATER); SIDE-11 8 findings (3 MUST, 5 LATER).

## SIDE-19 Parent watchdog and graceful shutdown

- MUST — the SIGNAL tag is missing. `S/modes/sidecar-mode.ts:595-599`: `onSignal` takes no signal name and logs nothing, so "the sidecar logs SIGTERM and SIGINT and shuts down" is half done. No test sends a signal to the shutdown path. Fix: register one handler per signal that logs `logger.child("SIGNAL")` with the name, then calls `shutdown`; test it with an injected process port.
- MUST — `S/shutdown.ts:4-13`: the header is false in three places. It says shutdown "closes the HTTP and socket servers" (there is no HTTP server, SIDE-02), lists the order "stop accepting new work, stop agents, flush events, close the socket, close the logger" (the real order, sidecar-mode.ts:574-585, is stop agents, flush events, close socket, close app tools bridge; there is no accept-stop and no logger close), and says "stops every agent (without a checkpoint)" with no test for it. Fix the header to the real steps.
- MUST — `S/shutdown.test.ts:48-73`: theater test. It builds its own list of steps, including a "close outbox" step with a 1 s limit, and asserts that the limits it passed in come back. Production has no such step: flush is limited to 10 s (`sidecar-mode.ts:581`). Item "Outbox close at shutdown has a 1 s limit" is not met. Fix: build the production step list in a function that the test calls, and put the 1 s outbox close in it, or drop the claim.
- MUST — `S/watchdog.ts:68-91`: the parent check and the idle sweep share one tick, and a tick that finds `ticking` set does nothing. A slow or hung `processes.sweep()` (a dispose waiting on an agent exit) blocks every later parent check, so a dead app can leave the sidecar and its agents running; "exits within 2 seconds when its parent dies" cannot hold. Fix: run the parent check on its own timer, before and apart from the sweep; test with a sweep that never resolves.
- LATER — `S/modes/sidecar-mode.ts:400` and `S/shutdown.ts:39-42`: the step timeout is a `setTimeout` that is never cleared when the step finishes first. Each shutdown leaves up to four timers of 5 to 10 s pending. The process ends with `process.exit`, so it is harmless today, but it breaks the "release every timer" rule. Fix: make `Timer` return a cancel function.
Outcome: fixed already, baf8138e — `Timer` now returns a `TimeoutHandle` whose `cancel()` is called in `finally` (`packages/sidecar/src/shutdown.ts:34-65`), and the production timer clears its `setTimeout` (`modes/sidecar-mode.ts:597-606`).
- LATER — no test covers the shutdown wiring in `runSidecarMode`: order of steps, a second request ignored (`finished`), exit code 0, parent gone leading to `finish`. Only the two units are tested.
Outcome: fixed already, baf8138e — `sidecar-mode.shutdown.test.ts` now covers step order and limits, a second request ignored, exit code 0, and parent-gone (`packages/sidecar/src/modes/sidecar-mode.shutdown.test.ts:72-204`).
- LATER — `S/modes/sidecar-mode.ts:140,606` reads `CONDUCTED_PARENT_PID`; `apps/desktop/src-tauri/src/sidecar.rs:37` says Rust sets it, but no code does (PLAT-09 is a stub). The fallback is `process.ppid`. Fine for now; make PLAT-09 set it, or remove the variable.

## PLAT-08 Saved terminal scrollback (`terminal_history.rs`, `pty.rs`, `lib.rs`)

- MUST `lib.rs:663-686` with `pty.rs:610-624`. History is saved only by the exit-watcher thread after `child.wait()`. At app quit, `RunEvent::Exit` kills the terminals, runs `shell::terminate_all` and the sidecar shutdown, then returns, and the process ends. Nothing joins or waits for the watcher threads, so the save races the exit and is likely lost for every terminal still open at quit. That is the main case the feature exists for (read it back after a restart). The issue rule says "saved after a debounce and flushed on exit"; the header's "no debounce" choice drops the debounce but the flush on exit is not there either. Fix: on `RunEvent::Exit`, save every live session's recorder synchronously (before or instead of relying on the watcher), and add a test that quits with a live terminal and finds the file.
- MUST `terminal_history.rs:31-33` against `settings.ts:1415` and the issue ("Scrollback limit caps the bytes kept for saved terminal history", "default 10 MB, clamped 1 MB to 1 GB"). The saved file is capped by the constant `MAX_ENTRY_BYTES` (20 MiB). The setting `terminal_scrollback_limit_bytes` never reaches Rust, and its description ("how much terminal output to keep") is false for saved history. The header calls this a design choice, but I found no ruling from the user for it in `docs/decisions.md` (D014 covers encryption only). Fix: pass the limit into the recorder at `pty_spawn`, or get the user's ruling and cut the item from the issue and the setting text.
- MUST `terminal_history.rs:15-16`. "Cutting must not start in the middle of an escape sequence: drop everything up to the first newline." `newest_bytes` falls back to cutting at the raw byte when the window holds no newline (`terminal_history.rs:240`), which can start inside an escape sequence or a UTF-8 character. Fix: keep the claim only for the newline case and say what happens otherwise, or skip to the next ESC-free boundary; add a test for the no-newline case (the current test asserts the raw cut as correct).
- MUST `pty.rs:589-590, 619-623`. `let _ = history.push_output(..)` and a failed `history.save(..)` is only `eprintln!`ed. A user who relies on restored scrollback never learns it was not written (engineering.md: "an error that is only logged", "`let _ =` on a Result"). `push_output` returns a `Result` that can never fail, which invites this. Fix: make `push_output` return `()`, and send a save failure to the UI (an event on `pty://exit` or a field on it) so a toast can show it.
- LATER `terminal_history.rs:168-185`. A file named `.x.tmp-1.bin` matches both the entry test and the temp test; the temp branch wins, so it is removed after one day and never counted in the size total. Only reachable with an odd terminal id, which `pty.rs` makes itself. Fix: check temp first and require the `.bin` entries not to start with a dot.
- LATER `terminal_history.rs:84-94`. At the cap, every output chunk drains the front of a 20 MiB `Vec` (a full memmove per chunk), and a recorder holds up to 20 MiB per terminal even if no input ever arrives. With many busy terminals this is heavy. Measure first; a ring buffer or chunk list fixes it. A recorder that never sees input could also drop its bytes.
- LATER `terminal_history.rs:116-128`. `history_dir` runs `evict`, and an eviction error (one file that cannot be removed) fails the whole load. Fix: report the eviction error separately from the load.
- LATER `pty.rs` and the UI. `platform.pty.loadHistory` has no live caller outside tests; the wiring is RUN-07 (`ui.tsv:1013`, `partly`). Nothing to do here but keep that row.
- Header agreement: all other lines of the header are kept by code and tests (paths, modes 0700/0600, atomic write, stale temp file, eviction by age then size, `history_not_found`, `history_bad_id`).
- Tests: size and age eviction, modes, temp-file cleanup, bad ids and the no-input rule have real tests. No test for: flush on exit (item above), the setting cap, the 14-day limit through `history_dir`, or `pty_load_history` as a command. The checklist items "Terminal rows keep replay sequences and screen modes" and the `terminal_sessions` columns are not in this file and have no test (they belong to pty/DATA work; confirm an owner).
- Duplication: none found inside the file. `pty.rs` has `encode_base64`, which is reused rather than copied.

## PLAT-12 On-device dictation (`speech.rs`, `ConductedSpeech/OnDeviceSpeech.swift`, `build.rs`, `Info.plist`)

- MUST `speech.rs:466-474`, `OnDeviceSpeech.swift:300-303`, header lines 17-19. The header says `speech_available` "answers false on the same conditions" as the unavailable case ("speech permission or language assets missing"). The Swift check only tests `supportsOnDeviceRecognition`. A denied or restricted speech permission still answers true, so the UI shows the button and the user gets the error only after pressing it. Fix: also check `SFSpeechRecognizer.authorizationStatus()` (not-determined stays available), or cut the claim.
- MUST `speech.rs:828-876`. The test named in "Test first" feeds the fixture WAV only into `Level` events. The partial and final texts ("the quick", "the quick brown fox") are hard-coded in the fake engine and then asserted back. The test would pass with a recogniser that returns nothing real. This asserts the fake's own words, so the "Final with the spoken words" claim is not tested at all. Fix: either a real-engine test that feeds the WAV to the Swift bridge (an `#[ignore]`-free macOS test, if speech assets exist on the runner) or cut the claim from the header and the issue and say the recogniser itself is verified by hand.
- MUST `speech.rs:242-293` with `speech.rs:411-528` and `OnDeviceSpeech.swift:300-309`. Possible deadlock or crash (found by reading, not run). The bridge callback upgrades a `Weak` to an `Arc<Session>` on the Swift queue. If `Dictation` has already dropped its `Arc` (cancel takes it out of `active` and drops it), the callback thread holds the last strong reference. Dropping it then drops `BridgeSession`, which calls `conducted_speech_free` → `shutdown()` → `queue.sync` on the queue the thread is already running on. That is `dispatch_sync` onto the current queue. The comment at `speech.rs:198-199` says this cannot happen, but nothing enforces it. Fix: do the free on a different thread (hand the `BridgeSession` to a detached thread), or hold the session in a registry until the bridge sends `Ended`.
- MUST `speech.rs:326-338`. When the engine is unavailable `start` sends `Error` + `Ended` on the channel and also returns `Err(speech_unavailable)`; the same failure reaches the UI twice (two toasts if both are shown). The `Err` start path (`report_failure`) does the same. Fix: pick one route; the channel is what the header calls "the only way text leaves".
- LATER `speech.rs:54-70` against the issue ("events transcript, levels, finished, failed, unavailable, microphoneDenied"). The event set is `Partial/Final/Level/Error/Ended`, with `unavailable` and `microphone_denied` as error codes. The header does not mark this as a design choice. Add the line "Our design choice: errors are one `Error` event with a code" or follow the research names.
- LATER header line 21-23 / `speech.rs:379-390`. The five-second limit is only tested with a 50 ms timeout; the 5 s constant itself is never checked. Add `assert_eq!(STOP_TIMEOUT, 5s)`. The Swift side also has a 4.5 s timer (`OnDeviceSpeech.swift:121`) that is not in the header.
- LATER `speech.rs:1045-1063`. Two tests only grep source text (`requiresOnDeviceRecognition = true`, plist keys). They are guards, not behaviour tests; fine to keep, but they do not show that audio stays on the device.
- LATER. `speech_start` takes an `onEvent` channel; the UI side (Ctrl+Shift+D, waveform, Voice mode, toasts) is COMP-08 (`ui.tsv:302, 529, 997, 998`). Not part of this batch.
- Header agreement: busy code, cancel sends only `Ended`, stop with nothing running, dead webview releases the microphone, and the plist strings are all kept and tested. The Info.plist and entitlements (`audio-input`) match the header.

## PLAT-14 Resource usage (`resource_usage.rs`, `platform/tauri.ts:508-514`)

- MUST `platform/tauri.ts:509-511`. The only caller passes `workspacePaths: []`, so every process has `workspace_path: None`. "Grouped by workspace" never works end to end; the header says "workspace paths come from the UI as an argument" and the Platform `resourceUsage()` takes no argument to carry them. The same function does `if (!result.ok) throw result.error`, which throws for an expected failure (engineering.md "Failure lives in the return type"). Fix: give `resourceUsage(workspacePaths)` an argument and return a `Result`; APP-07 then passes real paths.
- LATER `resource_usage.rs:97-101`. Each call builds a fresh `System` and reads the working directory of every process on the Mac, though only the app's tree is reported. The header claims it is "cheap enough to poll every few seconds"; it is not measured. Fix: measure on a busy Mac; refresh only the tree's pids if slow.
- LATER `resource_usage.rs:171-185`. `workspace_for` compares paths without resolving symlinks. The OS reports a real path (`/private/var/...`), a workspace given as `/var/...` or through a symlinked folder will not match. The test uses `std::env::temp_dir()`, which on macOS is a symlinked `/var/folders` path unless `TMPDIR` is already real; I could not run it to see whether that holds locally. Canonicalise both sides.
- LATER `resource_usage.rs:15-16` against the research ("memory footprint per terminal and sidecar"). The code reports resident size and says so (honest header). D020 asks for Conductor's behaviour; footprint is the number Activity Monitor shows. Decide.
- LATER. Tests do not cover the second-call path: only `percent_between` in isolation and a first-sample baseline of 0.0. No test hands `collect_usage` a prefilled `previous` map and checks a busy process returns a non-zero percentage, or that pids that vanished are dropped from the map.
- Header agreement: tree-only, no command lines, vanished process skipped, blocking pool: all kept.
- Duplication: none.

## PLAT-26 Online and offline (`network.rs`)

- MUST `network.rs:90-110` and `network.rs:163-167`. Newest-answer race. `network_status` reads the live flags, then stores them; the reachability callback on the watcher thread reads the stored value and stores its own. If the callback fires between the command's read and its `set`, the command writes an older answer over the newer one. The stored value then says "online" while the Mac is offline, and the callback for that change has already gone, so no later event corrects it (the next real change is compared to a wrong baseline). Fix: take one lock around "read state, compare, store, emit", and let `network_status` only report, not write, or give each answer a sequence number. Add a test with two overlapping answers arriving in the wrong order.
- LATER `network.rs:37-38, 60-66` against Conductor's `SCDynamicStore` approach. The probe is a route to `1.1.1.1`. A Mac on a LAN with no internet (or behind a captive portal) still reports online. The header states the choice but the research (A5) logs "Failed to create network change store" for a store-based watch; D022 asks for the same look and behaviour. Decide with the user whether route-reachability is acceptable.
- LATER `network.rs:131-145`. The watcher thread runs `CFRunLoop::run_current()` forever and has no `stop` (engineering.md "whatever subscribes unsubscribes"). It lives for the process lifetime, which is fine for the app, but the rule asks for a dispose or an explicit note.
- LATER `lib.rs:584`. A watcher that cannot start returns an error from `setup` and aborts app start. The header states "an error, not a silent startup", but taking the whole app down for an offline badge is harsh; confirm it is wanted.
- LATER. No test drives the real `SCNetworkReachability` callback, so the item "A network change watcher notices going offline or online" is only tested through `publish_change`. `plat_26_network_status_reads_the_live_state_and_stores_it` would pass if the watcher were never started.
- Duplication: the private `lock` helper at `network.rs:56` is a copy of `speech.rs:141` and `notifications.rs:114` (MUST, see "Across the batch").
- Header agreement: the "every change reported once" and "same rule for command and watcher" lines are kept (single `read_online`, `online_from_flags`).

## PLAT-27 Startup hardening (`lib.rs`)

- MUST `lib.rs:201-224` with header lines 24-27 ("with `panic = "abort"` in release builds the hook is the only record"). The hook only queues the record to the log writer's channel (`queue_rust_log` → `try_send`). The release profile aborts straight after the hook returns (`Cargo.toml:71`), so the writer thread most likely never writes the line. In a release build the panic report is therefore probably lost, which is the case the header calls out. Fix: in the hook, write the record synchronously (to the log file, or `flush` through a handle the writer offers) before returning; add a test that panics in a child process and finds the line in the file. Also the test `plat_27_a_panic_message_reaches_the_log_queue` only proves the queue, not the file.
- MUST `lib.rs:575-577` with header line 26-27. If the instance lock cannot be taken for any reason other than "held by another copy" (folder not creatable, open fails), the error is only `eprintln!`ed and the app starts with no guard. Two copies then share one database. This is the "silent fallback" in the banned list. Fix: surface the failure (dialog or refuse to start), and test it.
- MUST `lib.rs:574-578`. The guard runs inside `setup`, after the Tauri builder has created the window and started its plugins (the window-state and SQL plugins). A second launch therefore briefly builds a window and runs plugin start-up before it exits. Fix: take the lock at the start of `run()`, before the builder (the file path needs the app-data folder; read it from the bundle identifier), or accept and say so. Also the panic hook is installed inside `setup`, so a panic during builder or plugin start-up is outside it: install it first thing in `run()` with a stderr fallback, then wire the logger later.
- LATER. The lock lives in the app data folder named by the bundle identifier `build.conducted.app`; `tauri dev` uses the same identifier, so starting a dev build while the installed app runs makes the dev build exit and focus the installed one. Use a different identifier for dev, or a per-channel lock name.
- LATER `lib.rs:306, 321`. `SIGHUP` is defined in `lib.rs` while the other signal numbers live in `process_group.rs`. Move it next to `SIGTERM` and `SIGKILL`. Also `lib.rs` declares its own `getrlimit`, `setrlimit` and `flock` externs; fine without a `libc` dependency, but they are not tested for the macOS `OPEN_MAX` limit (the target 10,240 equals `OPEN_MAX`, so it works today).
- LATER `lib.rs:145-160`. `prepare_shell_state` runs the login-shell capture before the runtime, blocking window start-up for as long as the user's shell takes. I did not find a time limit on the call in this file. Check `shell::capture_login_env` for one; the failure path logs to stderr only and falls back to the default state, which `shell_login_env` then retries.
- LATER. Tests: the file-limit test passes if `raise_file_limit` does nothing and the limit was already high (it asserts `after >= before`). The pure `next_soft_limit` tests cover the logic. The panic hook itself (install, chain to the previous hook) and `guard_single_instance`'s exit branch have no test. `plat_27_closing_the_app_ends_every_terminal` tests `terminate_terminals`, not that `RunEvent::Exit` calls it.
- Header agreement: the file limit, PATH-before-runtime and terminal teardown lines are kept. The Pool pin item ("sql plugin 2.6.0 ... serialised queue meanwhile") has no code; it is a note only, which is fine.

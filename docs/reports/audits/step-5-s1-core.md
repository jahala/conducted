# Audit n5-s1-core (branch overnight/step-5)

Method: read the committed branch (`git show overnight/step-5:<path>`), the two issues (#4, #98), CLAUDE.md, architecture, engineering, and `sessions-and-chats.md` "What happens when you send a message". The test suite was not run.

## CHAT-02 Send a message as a new turn

Files: `apps/desktop/src/core/services/sessions.ts`, `sessions.chat-02.test.ts`.

- MUST `sessions.ts:458-460, 522-534` (header lines 14-15, "a message is stored as pending before the sidecar is asked"). Research step 1 says the UI writes the user row to SQLite with a `turn_id` before it sends `query`. The code only puts the message in the in-memory `sending` map. A crash between that point and the sidecar's `user_message` event loses the message with no trace. The header and the test name ("stores the message before the sidecar gets it") read as durable storage. Fix: either write the user row (or a queued-style row) through the repository before the request, or change the header, the issue line and the test name to say the pending state is in memory, and record that as a decision.
- MUST `sessions.ts:704-709`. The compare-and-set `UPDATE sessions SET config … AND config = $4` is written inline in the service. `SESSIONS_SQL.setConfig` and `repositories.sessions.setConfig` (`core/db/sessions.ts:105, 229`) hold the unconditional version of the same write. Two homes for one rule. The inline version also uses `JSON.stringify` and bypasses `stringifyJson`, which is the checked codec. Fix: add `setConfigIf(id, expected, next)` to the sessions repository next to `setConfig`, and call it here.
- MUST `sessions.ts:699-701`. The compare-and-set compares `JSON.stringify(session.config)` with the stored text. If the stored text has a different key order or whitespace (an older row, or a write from another path), the compare never matches and every config update is silently dropped as "lost the race", returning ok. Fix: compare on the stored text read back, or on the parsed value, and return an error when the loser cannot adopt a newer config.
- MUST `sessions.ts:494-520` (`#launchFor`). With no `launchFor` dep it builds a launch with `env: {}` and `providerKeys: {}` and silently skips an empty executable path or provider. The comment says SIDE-21 replaces it. That is a stand-in default on the live send path with no placeholder marker. `container.ts` should be checked for passing `launchFor`; if it does not, the sidecar gets no keys. Fix: require `launchFor` in the deps and fail the send with a clear error when it is missing, or mark it `notImplemented("SIDE-21")`.
- MUST `sessions.ts:132-140, 947-981` plus `model.ts` / `hooks.ts`. The "Message not sent" with Retry and Discard item has a service, but `failedSends` is not in `ChatView` and `chatView()` (line 892) does not return it. No component reads it (`UserMessage.tsx` only mentions it in its header). The state is stored and unreachable from a screen, so the checklist item "state: Message not sent with Retry and Discard" is not delivered. Fix: expose `failedSends` in `ChatView` and render the row in the chat; or set the item back to "partly" in the issue.
- MUST `Composer.tsx:168`. The toast reads "Couldn't send the message". The issue (inventory:toast row 601) and `docs/plans/items/system.tsv:2130` say "Couldn't send message". There is also no test for the toast. Fix: use the research text and add a component test that a failed send shows it.
- MUST `Composer.tsx:164-170` with `sessions.ts:475-479`. A failed send is kept in `failedSends` and the composer also keeps its draft (it returns before clearing). Discard then appends the failed text to the draft (`sessions.ts:975`), so the text appears twice. Fix: let the service own failure (clear the composer on accepted-for-retry), or have Discard skip the merge when the draft already holds the text. Add a test.
- LATER `sessions.ts:458`. `firstMessage` is derived from `lastIdx === null`. Two fast sends before the first `user_message` event is stored both say `firstMessage: true`. The sidecar's duplicate guard is the only protection. Add a test for two sends in a row, or pass the flag from the service state.
Outcome: open, item CHAT-02 (`firstMessage` is still `last.value === null` from the stored events, `sessions.ts:833`).
- LATER `sessions.ts:487`. `setting<string>("custom_prompt_general") ?? ""` hides a missing key. Settings registry defaults should make this unreachable; drop the `??`.
Outcome: fixed already, 9bc7e9f2 the service reads the setting with no `?? ""` fallback (`sessions.ts:883`).
- LATER `sessions.ts:608-615`. The default mode treats any value other than `"queue"` as `"steer"`, including unknown strings. Match the setting's enum and error on others.
Outcome: open, item CHAT-02 (`defaultMode` is still `=== "queue" ? "queue" : "steer"`, `sessions.ts:984-985`).
- LATER tests (`sessions.chat-02.test.ts`). There is no test for: an attachment materialisation failure (`#prepareAndSend` returns early, the draft is untouched); a steer that fails (the failed row has `delivery: "steer"`); `sendInstruction` with `options.config` going through `updateConfig`; a CAS loser when the sidecar request itself fails. The sidecar and composer are `vi.fn` stand-ins; there is no contract test tying them to the real `SidecarClient` shape (engineering.md "Stand-ins are checked against the real thing").
Outcome: open, item CHAT-02 (no attachment-materialisation failure test, and the sidecar and composer are still `vi.fn` stand-ins with no contract test, `sessions.chat-02.test.ts:71-108`).
- Checklist coverage: query rpc, preferences text, follow-up queue, CAS rule, and Retry/Discard logic each have a test that fails without the feature. Items with no test that would fail: the "Couldn't send message" toast; the UI send path for `SessionConfig` (the item moved from COMP-02, no component test drives `send` with the config); the "Message not sent" screen state; "the agent run lifecycle handles completion and cancel" (only `turn_ended` clearing is tested; cancel is `notImplemented("CHAT-05")` and the item is marked done).

## WS-01 Create a workspace: fetch, worktree, place name, branch prefix, port

Files: `core/services/workspace.ts`, `core/git/worktree.ts`, `app/CreateWorkspacePage.tsx` and their tests.

- MUST `workspace.ts:239-262, 383-406`. `create` and `retrySetup` repeat the same sequence (createWorktree, prepareWorktree, transition to ready, `#fail`). Extract one private `#materialise(workspace, repo)` and call it from both.
- MUST `workspace.ts:239-265`. The `warning` returned by `createWorktree` (offline fallback, failed post-checkout hook) and by `prepareWorktree` (config skipped) is dropped. Three checklist items ("tell the user when the fetch fell back to offline", "a warning text is shown when the worktree config steps are skipped", "a failing post-checkout hook is only a warning") are therefore not delivered: the constants exist and no code shows them. `worktree.test.ts` proves the strings are returned; nothing proves a user sees them. Fix: return warnings from `create` (for example in the `Workspace` result or a store field) and toast them from the page, with a test.
- MUST `workspace.ts:266-269, 247, 255`. The first chat is created only after git success. When creation fails, no session exists, so `recoverPrompt` → `firstDraftOf` returns `workspace_draft_missing` ("Recover prompt" cannot work in its main case). `retrySetup` also never creates the first chat, so a successful retry loses the prompt. Fix: keep the prompt on the failed row (or create the chat first, as the research flow does) and have `retrySetup` create it. The tests (`recoverPrompt`, `retrySetup`) seed a draft by hand and so hide this.
- MUST `workspace.ts:266-269`. If `createFirstChat` fails, `create` returns an error while the workspace is `ready`. The page then shows "Failed to create workspace" and stays on `/create`; pressing Create again makes a second workspace. Fix: return ok with the workspace and report the chat failure separately, or fail the row.
- MUST `workspace.ts:180-271`. `input.sectionId` is never read. The checklist item "add the new workspace to the chosen section, and say so on failure" has no code and no test, and the page sends a value that goes nowhere. Fix: call the sections service after the row exists and toast "move it from the sidebar" on failure.
- MUST `container.ts:85, 340` with no production source. `PlaceNames` is only supplied by test stubs (`pick: () => "place"`). Nothing implements "random city name from rarity tiers, skipping used names", and `createContainer` has no non-test caller on this branch. Header line 23 calls the list "a separate product decision", but the issue lists the rule as part of WS-01. Fix: add the real source (our own list, D002) with a test that it never returns a taken name, or move the two items out of WS-01 in the backlog.
- MUST `worktree.ts:10-11` and `296-308`. The header and the issue say a branch name is checked against local branches, remote branches and open or merged PRs. `branchNameIsTaken` checks only the first two and the test file has no PR case. Fix: add the PR check (via the GitHub service) or correct the header and the issue.
- MUST `workspace.ts:219-222` with `210-217`. Name, branch and port are chosen from one read and then written later. Two creates started together can pick the same port (`workspaces.port` has no UNIQUE) and the same folder. `(repo_id, directory_name)` is UNIQUE, so the second create fails with a raw database error instead of the next `-vN`. Fix: serialise creates inside the service (a promise chain) or retry on the unique conflict, and add a test that starts two creates at once.
- MUST `workspace.ts:143, 52, 221`. `deps.ports.allocateForNewWorkspace` is required by the deps type but never called. Port choice is inlined with `allocatePort` + `listPorts`, while `PortService.allocateForNewWorkspace` stays `notImplemented("RUN-03")` ("Picks a free block using the ports of all workspaces"). Two homes for one rule. Fix: call the port service here (RUN-03 supplies it) or drop the dependency and the stub.
- MUST `workspace.ts:197-201, 210-217, 243, 388, 391`. The remote is hard-coded as `"origin"` in four places, and the base is `repo.defaultBranch`. The checklist items "Remote origin (repo) picks the remote used for fetch and push" and "Branch new workspaces from (repo) picks the base branch" have no code. Fix: read both from the repo config.
- MUST `CreateWorkspacePage.tsx:107-117` against `container.ts:317` (`defaultSessionConfig`). The page builds its own `SessionConfig` with `agent: "claude"`, `model: "default"`, effort fallback `"high"` and a literal `appTools` object. The container already has one default-config rule. This is duplicated logic and an invented default. Fix: use `sessions.createFromDefaults` / `defaultConfig(repoId)` and pass only the user's changes.
- MUST `CreateWorkspacePage.tsx` header lines 6-8, 15-16. The header says a failed create keeps the draft with "Recover prompt" and that creating "shows progress". The page has no Recover prompt, no Retry, and no failed-workspace screen (`workspaces.recoverPrompt` and `retrySetup` are not called anywhere in `app/` or `features/`). It shows a toast and an inline error. Fix: wire both actions or change the header and the issue.
- MUST `CreateWorkspacePage.tsx:128-137`. The component renders a free-text model `Input`, a free-text branch `Input`, and a native checkbox. The issue and ui-map 3.9 call for a repo picker with "Switch repo / Add repository", a target-branch picker, a model picker with plan mode and attachments, and the shared composer toolbar. The header admits two of these. Since the page is marked `done`, the checklist items "Model picker, plan mode and attachments", "Target branch picker", "New-workspace form reuses the same editor and toolbar" are not delivered (D020, D022).
- MUST (checklist items with no code anywhere on the branch): Cmd+N and Tab/Shift+Tab; the dialog variant and the `experimental_new_workspace_page` switch (the setting is registered but the page is the only route); deep links with prefilled path, branch and prompt; the entry points other than the `/create` route; the shell-environment warm-up after the worktree exists; the later `push.autoSetupRemote` re-check (services-map 3.13); the passport country and coordinates. Either build them or set the issue items back to open and move the row off `done`.
- LATER `worktree.ts:129-138`. Any `rev-parse HEAD` failure triggers an empty initial commit, including a broken repository. Check the "unborn HEAD" message first.
Outcome: fixed already, 9bc7e9f2 the failure is matched against `UNBORN_HEAD_PATTERN` and any other error is returned (`worktree.ts:70-74, 258-262`).
- LATER `worktree.ts:164-198`. A fetch failure of kind `other` is reported as "Couldn't find origin/main", which hides the real cause. An offline failure with no cached ref returns the raw fetch error with no friendly text. Return the classified message in both cases.
Outcome: fixed already, 9bc7e9f2 an offline failure without a cached ref now returns `OFFLINE_NO_CACHE_MESSAGE`, auth `BRANCH_AUTH_MESSAGE`, and `other` returns `git_fetch_failed` with the real message (`worktree.ts:191-223`).
- LATER `worktree.ts:119-127`. `worktreeExists` compares the path string with `git worktree list` output, which prints real paths. A symlinked workspaces root makes the hook-failure downgrade fail. Compare real paths.
Outcome: fixed already, 075e4b4e `worktreeExists` also asks `git rev-parse --show-toplevel` inside the new folder and compares the real path (`worktree.ts:244-250`).
- LATER `workspace.ts:76-80`. `branchPrefixFor` treats any unknown type as `github_username` and an empty login as no prefix, silently. Match the three enum values and surface "GitHub login not found" as a warning.
Outcome: fixed already, a8f77de7 `branchPrefixFor` returns `""` for an unknown type (`workspace.ts:289-296`) and a missing login now yields the `GITHUB_LOGIN_MISSING_MESSAGE` warning (`workspace.ts:2361-2367`).
- LATER `CreateWorkspacePage.tsx:105-143`. `toast("Creating workspace…")` has no matching dismissal, and the error is shown twice (inline alert and toast).
Outcome: fixed already, 1a638b00 the page keeps the toast handle and calls `toast.dismiss(progress)` when creation ends (`CreateWorkspacePage.tsx:539-541`).
- LATER tests. `workspace.test.ts` stubs git, the placeNames source and the sessions port, and covers only the happy path, the custom prefix and one worktree failure. Not tested: `github_username` prefix; taken name and branch giving `-v1`; a taken port block; an offline warning reaching the caller; a prepare failure; the section; concurrent creates; a no-remote repository in the service. `CreateWorkspacePage.test.tsx` has one test (the happy path); the failure, empty-prompt, no-project and "branch" paths from the header's "Must handle" line are untested.
Outcome: open, item WS-01 (most cases are now tested, including the `github_username` prefix at `workspace.test.ts:513`, `-v1` at `:723`, the offline warning at `:626`, the section at `:700` and concurrent creates at `:713`; a taken port block, a prepare failure and a no-remote repository still have no test).
- Checklist items with a real test that fails without the feature: `nextFreeName` (-vN, 1000 tries), fetch classification, empty-HEAD commit, offline cached ref, hook-failure warning, branch clash message, worktree config skip, `.context` exclude, `branchNameIsTaken` local and remote, prefix building, folder layout, state `initializing` to `ready`/`failed`.

Summary: CHAT-02 has 6 MUST and 3 LATER findings plus 4 untested checklist items; WS-01 has 15 MUST and 7 LATER findings.

## CHAT-21 Fork a chat to a new workspace

1. MUST (duplicated logic) `core/services/checkpoint.ts:531-575` repeats `SessionsService.#forkInto` / `#storedEvents` (`core/services/sessions.ts:1876-1900, 1960-1968`). Both load every stored event of the chat, filter by `turnId`, and refuse with the same codes and messages (`chat_fork_turn_unknown`, `chat_fork_no_checkpoint`). Fix: put the turn lookup and checkpoint choice in one place (a sessions-service method that returns the turn's checkpoint id, which `forkToWorkspace` calls), and have `#forkInto` use the same one.
2. MUST (fake success in the return value) `core/services/checkpoint.ts:622` returns `{ ...target, activeSessionId: forked.value.id }`. Nothing writes that id to the workspace row or the workspace store; `SessionsService.create` never calls `workspace.setActiveSession`. The container test (`checkpoint.chat-21.container.test.ts`, `expect(forked.activeSessionId)`) only checks the returned copy, so it passes while the stored workspace still has `activeSessionId: null`. Fix: call `setActiveSession(target.id, forked.value.id)` (through a dep) and assert on `workspacesById[forked.id].activeSessionId`.
3. LATER `core/services/checkpoint.ts:580` creates the workspace with `from: { kind: "branch", name: source.targetBranch }`. `resolveBase` (`core/services/workspace.ts:1180-1195`) then runs a local `rev-parse`, or fetches the remote when no local branch exists, only for its answer to be thrown away because `presetBaseSha` wins (`workspace.ts:934`). A fork can therefore fail offline, or when the target branch is gone, although the commit is already known. Fix: skip `resolveBase` when `presetBaseSha` is set and take `targetBranch` from the input.
   Outcome: fixed already, d9dc93f3. createFromCommit skips resolveBase when presetBaseSha is set and only names the branch (workspace.ts:843-853).
4. LATER Order of work. The repo's setup script runs in `createFromCommit` (`workspace.ts` `#materialise` then `runSetup`) before the chat copy is checked. A fork that `#forkInto` refuses (`chat_fork_no_agent_message`, `chat_fork_unwired` for copying checkpoints) builds a worktree, runs setup, then removes it. Fix: validate the chat side first, or split the copy checks into a dry-run step.
   Outcome: open, item CHAT-21. forkToWorkspace still calls createWorkspaceFromCommit (checkpoint.ts:579) before forkSessionInto (:613), so the worktree and setup run before the chat copy can refuse.
5. LATER Optional deps `createWorkspaceFromCommit`, `forkSessionInto`, `removeWorkspace` (`core/services/checkpoint.ts` deps, ~line 135-150) turn missing wiring into runtime `chat_fork_unwired` errors. `discard` (`checkpoint.ts:590`) returns the failure without removing anything when `removeWorkspace` is undefined, which leaves an empty workspace behind. Make them required, so the type checker finds a missing wire.
   Outcome: open, item CHAT-21. The three deps are still optional (checkpoint.ts:138-149), and discard still returns the failure without removing anything when removeWorkspace is undefined (:583-586).
6. LATER Tests missing: the `chat_fork_unwired` branches, and the `discard` branch where `removeWorkspace` itself fails (the combined message). The 8 tests in `checkpoint.chat-21.test.ts` use fakes for the workspace and chat services; the real path is only in `checkpoint.chat-21.container.test.ts`, which has one case. No test for two forks of the same turn at once (the footer's `forkFlight` key is only exercised through one click).
   Outcome: open, item CHAT-21. Neither test file contains a chat_fork_unwired case, a removeWorkspace-failure case, or two concurrent forks of one turn.
7. LATER `features/chat/TurnFooter.tsx:132` casts the search with `as never` (and `:115` for CHAT-16). Use the workspace route's typed `WorkspaceSearch` instead of defeating the type check.
   Outcome: open, item CHAT-21. TurnFooter.tsx:167 and :184 still cast the search with `as never`.
8. MUST (backlog) `docs/plans/backlog.md:186` still has CHAT-21 as `stub` and issue #144 asks for `done` in the closing PR. No placeholder is left (`grep notImplemented("CHAT-21")` is empty), so `pnpm stubs` should refuse a `stub` row with none. Set the row to `done`. `docs/plans/items/ui.tsv:410` and `system.tsv:2237` still say `partly` / `missing`; update them in the same change.

## NAV-17 Deep-link routes

1. MUST (duplicated logic) `main.tsx:140-165` `openWorkspaceLink` still parses `conducted://workspace` and navigates, the same job as the `open-workspace` case in `app/deep-link-routes.ts:195-203, 297-309`. Its header comment and the issue's rule item ("the entry's openWorkspaceLink duplicates parseDeepLinkRoute") ask for one opener. The two also differ: the entry logs a warning for an unknown workspace, `openDeepLink` shows a toast. Fix: route notification clicks through `openDeepLink` (or `useDeepLinkOpener`), delete `openWorkspaceLink`.
2. MUST (header claim not kept) `app/deep-link-routes.ts:15-17` says the left-out hosts (`auth`, `gh-auth`, `automation`, `loadout`, onboarding, dev) "return an error result, so the caller can say the link is not supported". Code has no such branch: they fall to `default:` (line 261) and `parseCreateWithPrompt`. Result: `conducted://automation?id=1` gives "Invalid deep link", and `conducted://auth?code=x&prompt=hi` creates a prefilled workspace with prompt "hi" (checked with `new URL`: host `auth`, and the key `auth?code` is skipped). Fix: list the left-out hosts, return `deep_link_unsupported`, give it a title, and only treat a host as create-with-prompt when it contains `key=value` text (host ends in `=` or has `&`).
3. MUST (silent fallback) `app/deep-link-routes.ts:350-377` `create-from-plan`: when the named repository is not found it uses `firstRepoId()`, shows "Repository not found ... Using the first repository" and still starts the agent with the plan in the wrong project. A plan meant for one repo gets run in another. Fix: stop with the error, start nothing.
4. MUST (silent fallback) `app/CreateWorkspacePage.tsx:185-187, 210, 218-226` and `app/deep-link-routes.ts:381-388`. A `path` that matches no project is dropped in `create-with-prompt`. Either way the page opens on the first project and the user is not told the link named another.

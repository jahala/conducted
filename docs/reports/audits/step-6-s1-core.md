## CHAT-05 Cancel a turn

- MUST `apps/desktop/src/features/composer/Composer.tsx:11-13,141-155`: the header says Cmd+Shift+Backspace is a window listener "because the shortcut dispatcher (NAV-14) ... [is] not built yet". NAV-14 is `done` in the backlog and `useCommandHandler` exists (`app/command-dispatcher.ts:488`, used by `MessageList.tsx:69`). The registry entry `chat.cancelAgent` (`core/registries/commands.ts:940`) has no handler, so a user rebind in the shortcuts dialog does not move the cancel key and the hard-coded listener keeps firing. Fix: register `useCommandHandler("chat.cancelAgent", ...)` in the composer, delete the listener, and correct the header. The test at `composer-shell.test.tsx:225` should then press the key through the dispatcher.
- MUST `core/services/sessions.ts:706,723-730`: `cancel` calls `#closeInteraction`, which deletes `openInteractions[id]` but leaves the resolver and promise in `#interactionResolvers` and `#interactionPromises`. The sidecar's `requestInteraction` call for that card is never settled. The later `turn_ended` path cannot settle it either, because it looks the interaction id up in `openInteractions` (line ~1012), which cancel already emptied. This leaks the maps, and the handler promise stays open. Fix: in `cancel`, call `#settleInteraction(open.interactionId, {kind: "withdrawn"})` instead of deleting state directly. Add a test that the `requestInteraction` promise resolves with `withdrawn` after cancel. The existing test (`sessions.chat-05.test.ts:191`) only checks that the store entry is gone.
- MUST `core/services/sessions.ts:708-712`: `#clearSending` empties every pending send of the chat, not only the dropped ones. The message for the turn that is already running is also removed from the view until its `user_message` event arrives. Cancel also does not handle a `sendMessage` request that is still in flight: when it later returns ok, the message runs after the cancel and nothing restores it. Research (sessions.md 173) aborts queries that are still in setup. Fix: clear only the dropped ids, and for an in-flight send either await it first or mark it so a late ok restores it to the draft. Add a test for the in-flight case.
- LATER `core/services/sessions.ts:699-713` and `core/services/follow-up-queue.ts:145`: the pause is held in memory only (`pausedSessionIds`), and `setPaused` is still `notImplemented("CHAT-04")` (line 125). After an app restart the "paused after cancel" state is gone and the queue may release. The issue item "queued messages go back into the composer draft ... except ones already sending" is met only for sidecar-dropped messages. App-queue rows stay in the queue, paused. This is the documented design choice, but the checklist text still says "go back into the composer draft". Edit the item text to say "stay in the queue, paused", or build it.
Outcome: fixed already, e4149c1d `setPaused` now writes the pause to `sessions.queue_paused_at` and restores it (`core/services/follow-up-queue.ts:220-237`).
- LATER `core/services/sessions.ts:978-983` against `features/composer/Composer.tsx` (`working = live?.status === "working"`): two separate definitions of "working". The service adds the `cancelling` flag and the composer does not, so the Stop button is clickable again while a cancel is pending. Expose one selector and use it in both.
Outcome: open, item CHAT-05 - the composer still computes `working` from `live.status` and ignores the service's `cancelling` flag (`Composer.tsx:244`, `sessions.ts:988`).
- LATER `core/services/sessions.chat-05.test.ts`: the composer is a `vi.fn` mock and the sidecar is a canned `replyTo`. These stand-ins are not checked against the real `SessionManager.cancel` (`packages/sidecar/src/session/manager.ts:281`). A contract test on `droppedMessageIds` would close it.
Outcome: open, item CHAT-05 - the suite still uses a mocked composer and a canned sidecar reply.
- LATER `core/services/follow-up-queue.ts:150-175`: if one `sending` row cannot be set back to waiting, the reorder is skipped and the loop goes on. Rows then stay in a mixed order with no retry. There is no test for the partial-failure branch.
Outcome: open, item CHAT-05 - the partial-failure branch still has no retry and no test (`follow-up-queue.ts:150-175`).
- Checklist coverage: Stop button (`composer-shell.test.tsx:216`) ok; Cmd+Shift+Backspace (`:225`) ok but see MUST 1; requeue a sending row at the end (`follow-up-queue.chat-05.test.ts:135`) ok; restore to draft with attachments (`sessions.chat-05.test.ts:239`) ok; abort queued queries and bump the run id: no test in this batch (sidecar `cancelEpoch`; confirm a sidecar test exists); "cancel clearing the pending send" ok.

## WS-03 Setup script in a terminal, with workspace variables and copied files

- MUST `core/services/terminals.ts:499,516` and `core/services/run-scripts.ts:174`: `TerminalsService.runScript` (RUN-01), `TerminalsService.outputFor` (RUN-07) and `RunScriptsService.stopWorkspace` (RUN-01) are still `notImplemented`. Those items are `stub` in the backlog. `RunScriptsService.runSetup` calls the first two for any repo with a setup script, so creating a workspace throws, and `cancelSetup` throws on `stopWorkspace`. WS-03 is `done`, but its blockers list (#211 RUN-06) leaves out RUN-01 and RUN-07. All tests inject fakes, so the green CI proves nothing about the real path. Fix: either build RUN-01/RUN-07 in this step or set WS-03 back to `stub` and add the blockers. Add one test against a real `TerminalsService` with a fake PTY.
- MUST `core/services/workspace.ts:798`: `succeeded = exitCode === null || exitCode === 0`. A null exit code means killed or unknown (`terminals.ts` `close()` and `killAll()` call `#finish(id, null)`). So Stop from the Setup tab, or a script killed by a signal, ends as "completed" and the workspace goes to `ready`. Only "no script" (`run-scripts.ts:130`) should be success. Fix: return an explicit "no script" outcome and treat null as failed or cancelled. Test: a killed script.
- MUST `features/scripts-panel/setup/SetupTab.tsx:117-119` against `core/services/workspace.ts:826`: Stop calls `actions.terminals.close(terminalId)`. `cancelSetup` has no caller and is not in Actions. So the "Cancelled setup script" and "Stopping setup script..." states cannot be reached from the UI, and Stop produces "completed" (see above). `detecting` is also never set by any service. Fix: add `workspaces.cancelSetup` to Actions, call it from Stop, set `stopping` while it runs, and test the Stop click (`SetupTab.test.tsx` has no Stop test).
- MUST `features/scripts-panel/setup/SetupTab.tsx:105-114`: the results of `actions.sessions.send`, `actions.workspaces.retrySetup` and `actions.terminals.close` are discarded (`void run(...)`). A failed send shows nothing. The issue requires "Failed to attach setup logs" and "Failed to attach setup context", and neither string exists in the code. "Setup script failed. Check the setup tab for logs." exists only as an error message and is never shown as a toast (grep `SETUP_FAILED_MESSAGE`: one use). Fix: toast every failed result with those strings, and test each.
- MUST `core/services/run-scripts.ts:155`: the setup log is written to `${fs.paths.temp}/conducted-setup-<id>.log`. `docs/data-model.md:51` says `setup-logs/<workspace>.log` in app data, kept until the workspace is removed. Temp is cleared by the OS, nothing removes these files, and the path is stored in the database (`setSetupLogPath`). Fix: write to the app data folder as documented, and add a guard test for the lifetime. Also `outputFor(workspaceId, "auto", ...)` reads the workspace's "auto" source, not the terminal this run started (`started.value.terminalId`), so with a run script active it can return the wrong output. Pass the terminal id.
- MUST `core/services/workspace.ts:528-541`: on load, every `failed` workspace with a log path gets `exitCode: 1` and `interruptedReason = SETUP_INTERRUPTED_MESSAGE`, and every `ready` one gets `exitCode: 0`. These are invented values. A real script failure is shown after a restart as "The app quit while setup was running". Also a quit during setup leaves the row `initializing` with no log path (the path is saved only after the run ends, line ~801), so `continue` at line 530 skips it and the tab shows nothing. Fix: store the exit code and the reason, or leave them null. Record the log path at start ("Start setup: record state and the setup log path"). Test the load for each case.
- MUST `core/services/workspace.ts:716-722`: `#copyIncludedFiles` swallows errors. A failed `ls-files` returns ok (line 722), an unreadable `.worktreeinclude` becomes an empty list, a failed repo config falls back to `DEFAULT_COPY_FILES`, and files over 256 KiB, unreadable files or directories are skipped without any warning. Files are copied with `readText`/`writeTextAtomic`, which corrupts binary content and drops file modes. Directory patterns never copy: `ls-files --directory` returns `dir/` entries, which are matched and then skipped by `isDirectory`. Fix: return the skipped paths as warnings (the create page already shows warnings), copy bytes with the mode kept, and copy directories. Add tests that run `#copyIncludedFiles` against a real temp repo (today only the pure helpers are tested, `workspace.setup.test.ts:282-310`), and a test for the 256 KiB cap with a real file.
- MUST `core/services/workspace.ts:350-391` duplicates `platform/memory.ts:182` (`globToRegExp`) and its gitignore matcher. Two glob implementations with different rules for `**` and `?`. Fix: one shared matcher.
- MUST `features/scripts-panel/setup/SetupTab.tsx:34-41`: `SETUP_FIX_PROMPT` and `ADD_SETUP_PROMPT` are written in the screen file. `agent-instructions.ts` (header: "the text of every request the app makes through a chat") is the one home for these. The fix prompt also says "Read the setup log in the Setup tab", which the agent cannot see, and it attaches no log, so "attach the logs" is not met. Fix: add `fixSetupInstruction` and `addSetupScriptInstruction` to `agent-instructions.ts` with the log tail in the text.
- MUST issue items "Files to copy shows a glob preview, detects matching files and reads .worktreeinclude" and "Files to copy: ... default .env*" in the settings: `features/settings/repo/FilesToCopyField.tsx` is still `notImplemented("SET-07")`. Only the copy at creation is built. Either move the items to SET-07 in the issue or build the field.

# Audit n6-s1-sidecar (SIDE-06, SIDE-08)

Audited from `git show overnight/step-6:<path>`. Nothing was run. Ranked MUST first, then LATER.

## SIDE-06 Write-ahead event log

- MUST `packages/sidecar/src/outbox/replay.ts:40-52`: `replayAll()` breaks after the first call that finds no chat with pending events. The async IIFE runs synchronously when `sessionsWithPending()` is empty (no `await` is reached). Its `finally` sets `this.all = null`, and then line 51 sets `this.all = run`, so `this.all` keeps a settled promise for good. Every later `replayAll()` returns that stale promise and replays nothing. The common case is an app attaching while the log is empty, followed by a crash and a later reattach with events pending. `peer.onAttach` in `sidecar-mode.ts:164` calls `replayAll` on every attach. Fix: assign `this.all` before the body can finish, for example `const run = Promise.resolve().then(...)`, or clear it in `.finally()` on the returned promise as `replaySession` does. Add a test: `replayAll()` with an empty log, then append, then `replayAll()` delivers.
- MUST `packages/sidecar/src/outbox/event-outbox.ts:221-233`: `sweepIdle()` runs outside the per-chat serial queue. It reads `state.pending.length` and `updatedAt`, then awaits `moveToTrash`, then deletes the state. An `append()` for that chat that runs during the await writes new pending events to the file. The sweep then trashes that file and drops the state, so acknowledged-to-the-agent events are lost. This breaks write-ahead durability. Fix: run each chat's check and trash inside `deps.queue.run(sessionId, ...)` and re-check `pending.length` and age inside it. Add a test with an append interleaved with the sweep.
- MUST `packages/sidecar/src/modes/sidecar-mode.ts:811-841` (`createOutboxStorage.writeAtomic`): the directory fsync is missing. It does temp file, `sync`, `rename` and then nothing. The issue item "temp file with mode 0600, fsync, rename, fsync of the directory" and the header of `outbox-file.ts:7` and `:64` promise it. Without it the rename is not durable and the "write before send" guarantee is false after a power cut. Fix: open the directory read-only, `sync()`, close. Return a distinct error code (the test uses `outbox_dir_sync_failed`) when only that step fails.
- MUST `packages/sidecar/src/outbox/event-outbox.ts:146-157` and `:186-193`: `durabilityUncertain` is not what the header (`:22`, `outbox-file.ts:10-12`) and the issue say. Three gaps:
  1. Nothing makes `append` refuse. The header says "append refuses until a write succeeds". The code only reads the flag into `wasUncertain` to log "durable again".
  2. Any write failure marks the chat uncertain, not only a directory fsync failure. The storage port has no way to say which step failed, and the test fakes it with an error code that the outbox never reads.
  3. When the very first append for a chat fails, `current` is undefined, so nothing is recorded.
     The flag is also never exposed to callers, so no one can see "durabilityUncertain". Fix: decide the real behaviour (a refusing flag cannot clear itself with "the next successful write", so the header is self-contradictory). Then make the port report a dir-sync failure, store the flag in a state that exists even for a new chat, expose it, and fix the header to match.
- MUST `packages/sidecar/src/outbox/event-outbox.test.ts:206-232`: the test "a directory fsync failure marks durability uncertain until a write succeeds" would pass without the feature. It asserts that a warn line exists and that a retry succeeds. It never checks refusal, a flag, or that a non-dir-sync failure is treated differently. It also fails to cover the real storage. Fix: assert against the real behaviour once it is decided (see above).
- MUST No test covers the real `createOutboxStorage` (`sidecar-mode.ts:811`): file mode 0600, atomic rename, a leftover `.tmp` moved to the Trash by `open`, `trash` failure, a missing folder, `list` creating the folder. All outbox tests use `MemoryStorage`. The "stand-ins are checked against the real thing" rule is not met. Fix: add a storage test on a run-owned temp folder, ideally a shared contract test that runs against both `MemoryStorage` and the node:fs storage. The storage should also move out of `sidecar-mode.ts` into `outbox/` so it can be tested without starting the host.
- MUST `packages/sidecar/src/outbox/replay.ts:66-102`: `runSession` iterates a snapshot of `pending()` taken at the start. An `eventPersisted` notification that acks event N while event N-1 is in flight still gets event N sent (stale snapshot). The header (`:15`) says an ack during replay "acknowledges it once", which is true, but the app gets a duplicate delivery. This is safe by event id, so only a LATER note: re-read `pending()` after each ack, or skip entries no longer pending.
- MUST (corrected to LATER on re-read, see below) not used.
- LATER `packages/sidecar/src/outbox/event-outbox.ts:91-108`: `open()` fails the whole outbox on the first corrupt file. That matches "a bad outbox at start is fatal" in the issue, but the headers say "the chat is blocked" (`event-outbox.ts:20`, `outbox-file.ts` Must handle). One broken chat blocks every chat. Make the header say "the sidecar refuses to start" or block only that chat; the issue wording ("blocks the session") is the other reading. Pick one and align header, issue and test.
- LATER `packages/sidecar/src/outbox/event-outbox.ts:92-93`: `open()` calls `cleanTempFiles()` before `list()`. The `OutboxStorage` doc says `list()` creates the folder, and the node:fs `cleanTempFiles` does `readdir(root)` which fails with ENOENT on a missing folder. It works today only because `probeWritable` in `sidecar-mode.ts:168` makes the folder first. Call `list()` first, or make `cleanTempFiles` treat a missing folder as zero.
- LATER `packages/sidecar/src/modes/sidecar-mode.ts:828-842`: if `handle.writeFile` or `sync` throws, the handle is never closed (`handle.close()` is only on the success path). Use try/finally. The cleanup `rm(temp)` is allowed (the run created it), but then `cleanTempFiles` trashes `.tmp` files by a different route; one home for temp removal is simpler.
- LATER `packages/sidecar/src/outbox/event-outbox.ts:278-290` and `:294`: the monotonic and duplicate checks do not cover two entries with the same `eventId`; `append` does not reject an `eventId` already pending (a retry after a failed write whose rename actually landed could double-write). The `sort` at `:294` is dead after the strictly-increasing check. Remove the sort or the check.
- LATER Checklist items with no test that would fail without the feature:
  - "Outbox writes are atomic: temp file 0600, fsync, rename, fsync of the directory" (storage untested).
  - "The outbox root folder comes from an environment variable; ours requires it and has no default" (`config.test.ts` covers config; fine).
  - "Idle outbox files are removed by a sweep after 30 days" (covered with memory storage only, and the race above is uncovered).
  - "With no app connected, events are still queued in the outbox and requests are answered with an empty result" (belongs to the publisher; not in this batch's tests).
  - "Replay waits up to 10 s": only the option value is asserted, not a real timeout (acceptable, the timeout lives in the RPC peer).
  - "A non-retryable send error ... fails the turn visibly" (publisher; not in this batch).
  - The "Start the real host on a temporary socket path ... once FileEventOutbox.open and AppToolsBridge.start are real" item is marked `scaffold: missing`; `sidecar-mode.test.ts` has host tests but none reads `SOCKET_PATH=` after a pending event survives a restart.
- LATER `packages/sidecar/src/outbox/outbox-file.ts:16-18`: header says a file's modification time "would do as well, but the storage port has no stat call". That is a design note, not a bug. `updatedAt` is also set on acknowledge, which is what the sweep wants. No action.

## SIDE-08 Checkpoints

- MUST `packages/sidecar/src/checkpoints/checkpoint-service.ts:145-170` and `:194-210`: the "save, map exit code, log a skip" block is written twice, once in `take()` and once in `takeEnd()`. Two copies will drift. Fix: have `takeEnd()` call `take(request, "end")` after awaiting the start, and add the summary on the `created` result.
- MUST `packages/sidecar/src/modes/sidecar-mode.ts:785-807` (`runCheckpointer`): three issue items are not done.
  1. stderr is `"ignore"`, so `CheckpointerOutput.stderr` is never filled in production. The "output and error kept up to 64 KiB for the log line" item and the warn logs in `checkpoint-service.ts:168` and `:261` never get an error text in the real app. The script prints its reasons on stderr.
  2. The timeout kills only the direct child (`child.kill()`), not the process group, so git children of `checkpointer.sh` outlive a timeout. The issue says "SIGTERM to the process group, SIGKILL 5 s later". The child is not spawned detached, so there is no group to signal.
  3. stdout is read to the end with no cap; only the log line is cut later.
     Fix: spawn detached, signal `-pid`, capture stderr with a 64 KiB cap, and put the function in `checkpoints/` so it can be tested.
- MUST No test covers `runCheckpointer` (timeout, SIGTERM then SIGKILL, exit code, stderr). The 60 s limit checklist items ("Checkpoint run timeout of 60 s", "Watchdog: checkpoint run limit of 60 seconds", "A checkpoint save times out after 60 seconds: SIGTERM first, then SIGKILL") only have a test that the constants are passed to a fake runner (`checkpoint-service.test.ts:68-72`). Nothing proves a hung script is stopped. Fix: run a real `sleep`-like fixture script against `runCheckpointer` with small timeouts.
- MUST Duplicated checkpoint rules across runtimes: `apps/desktop/src/core/git/refs.ts:14-33` repeats `CHECKPOINT_REF_PREFIX`, `CheckpointPhase`, the exit codes (named `busy`/`unmergedIndex`/`notToplevel` against `skippedMergeOrRebase`/`skippedConflicts`/`refusedRootIsAncestor` here) and the id format (`turnCheckpointId` against `checkpointIdFor`). `bin/checkpointer.sh:60` is a third copy. `checkpointer-constants.test.ts` compares only the script and the sidecar. Nothing compares the UI copy, so a change on one side breaks revert and fork silently. The architecture rule is "a rule two runtimes share is written once, with a test comparing their answers". Fix: move the id format, prefix and exit codes into `packages/shared` (or `protocol`) and import them in both; or add a test that checks the UI constants against the script and the sidecar.
- MUST `packages/sidecar/src/checkpoints/checkpoint-service.ts:80-129`: a `start()` whose turn never calls `end()` (shutdown takes none, by design) leaves its record in `turns` forever; only `end()` deletes it. Bounded by process life, so low impact, but the data-lifetime rule says every growing store names its removal. Fix: delete the record when the turn is abandoned, or document the lifetime in the header.
- MUST `packages/sidecar/src/checkpoints/checkpoint-service.ts:212-215`: when the start checkpoint was skipped, the end checkpoint is still taken but carries no `changes` (tested at `checkpoint-service.test.ts:190`). The issue says "The end checkpoint lists the changed files, up to 200", and the research shows the end summary needs only the two ids. With the start skipped there is nothing to diff against, so this is acceptable, but the header does not say so and no Conductor source is cited for it. State the choice in the header ("Our design choice") or compare with the research in `sessions.md` section 7.
- LATER "The checkpointer script is run ... detached; a missing environment skips it" has no implementation and no test. There is no check for a missing workspace folder or missing script before spawning, only the spawn error path (`checkpoint-service.test.ts:101`).
- LATER `packages/sidecar/src/checkpoints/checkpoint-service.ts:24-26` (header): "this class is tested with a recording runner" and "tests run the real script against a temp repository only in the script's own test" mean no test exercises the sidecar with the real script. The `--id`/`--force` argument shapes and the `diff <a> <b> -- --name-status -z` contract are checked against a fake only. Add one contract test that runs `checkpointer.sh` in a temp repo through `ScriptCheckpointService` and compares the parsed `changes`.
- LATER `packages/sidecar/src/checkpoints/checkpoint-service.ts:224`: header line 20 says "the same id twice (a retry): the script gets --force". The code passes `--force` on every save. That is harmless but the header describes a conditional. Align the header.
- LATER `packages/sidecar/src/checkpoints/checkpoint-service.ts:246-253`: the two `diff` calls run one after the other with no overlap; they could run in parallel (two 60 s limits can add up to 120 s of waiting before `turn_ended`). Run them with `Promise.all`, or take the whole summary under one limit.
- LATER `packages/sidecar/src/checkpoints/checkpoint-id.ts:46-50` and `packages/protocol/src/events.ts:70`: `SkipReason` and the protocol `skippedReason` enum are two copies of the same list. Derive one from the other.
- LATER Checklist items with no sidecar test in this batch (they belong to other owners, listed so they are not lost): "A turn waits for the previous turn's end checkpoint", "An end checkpoint is taken on success, failure and cancel", "Shutdown takes no checkpoint", "The checkpoint event is durable", "One PreToolUse hook creates the start checkpoint / waits before any non-read-only tool" (SIDE-04 and the Claude runner; `turn.test.ts:595` covers `beforeFirstWrite`). Revert, fork and "Unable to fork chat" items live in the app (CHAT-15). I did not verify these.
- LATER `packages/sidecar/src/checkpoints/diff-summary.ts:36-56`: a `U` (unmerged) status maps to `modified` and an unknown letter is skipped silently, with no log. An unknown status drops a file from the summary without a trace. Log or count the dropped tokens.

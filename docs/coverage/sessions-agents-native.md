## Method

Research read in full: `overview.md`, `sessions-and-chats.md`, `sessions.md`, `claude-runner.md`, `other-runners.md`, `native-and-sidecar-map.md` (A to D). Scaffold read: every header in `packages/sidecar/src`, all of `packages/protocol/src`, every Rust module header and `lib.rs` in `apps/desktop/src-tauri/src`, `Cargo.toml`, `tauri.conf.json`, the capability file, the three migrations, the three `bin/` scripts, `docs/plans/tauri-commands.md`, `docs/data-model.md`, `docs/decisions.md`, `docs/plans/backlog.md`, `docs/plans/cloud-and-remote.md`. For UI-owned rows I also read the headers of `D/core/sidecar/*`, `D/core/db/repair.ts`, `D/core/services/{follow-up-queue,checkpoint,github,agent-instructions}.ts` and the settings registry, to see whether a shared rule has a home on both sides.

Rules used:

- One row per item. An item that several research docs describe gets its row in the doc with the most detail. The summary docs (`overview.md`, `sessions-and-chats.md`) only get rows for statements that no detail doc repeats.
- Recommendation lists in the research ("What to copy", "Blueprint", "Lessons") are not items. Their content is covered by the rows they summarise.
- Most bodies are still placeholders. "Covered" means a file with a named backlog id owns the behaviour in its header or in real types, so the work cannot be forgotten. It does not mean the code runs.
- "Deliberately different" cites a decision in `docs/decisions.md` when one exists. When only a file header records the choice, the cell says "header only", and the choice is listed under "Proposed decision entries" so the decision log catches up.
- Path shorthand: `S/` = `packages/sidecar/src/`, `P/` = `packages/protocol/src/`, `R/` = `apps/desktop/src-tauri/src/`, `D/` = `apps/desktop/src/`, `B/` = `bin/`.

Classes: **Covered**, **Partly** (the Fix column says what is missing), **Missing**, **Deliberately different**, **Out of scope** (team features, Piccolo, Conductor's analytics, internal-user tools, dead code), **Planned** (a CLOUD or RC id from the backlog).

## Findings that matter most

1. **The app is never told that plan mode changed behind its back.** A local plan approval is handled: the plan bar turns plan mode off (CHAT-12 header). An agent that enters plan mode by itself (`EnterPlanMode`, or the CLI starting in plan mode) is not: Conductor sends `enterPlanModeNotification` and echoes the config, ours sends neither. The same gap opens again when a plan is approved from claude.ai (RC-03). See sessions 5 and claude-runner 3.5. New id SIDE-20.
2. **Settings the protocol cannot carry.** The settings registry offers "Ultracode", "Ultra", Claude output style and Codex personality, and Codex approval policy. `SessionConfig` has no field for any of them, and `Effort` stops at `max`. The picker will show choices the sidecar cannot apply. New id AGENT-16.
3. **Custom agent program paths have no route to the sidecar.** Settings has `claude_executable_path`, `codex_executable_path` and `opencode_executable_path`. `Runner.detect` only searches the captured PATH, and no RPC or `StartOptions` field carries an override. New id SIDE-21.
4. **Sign-in flows stop halfway.** `startAgentLogin` returns a URL and code, but nothing finishes or cancels a login, and Cursor's flow must hand an API key back to the app. Extend SIDE-15.
5. **The logger mode has no launcher.** `S/logging` builds an HTTP logger (SIDE-18) and `tauri-commands.md` names `conducted-sidecar logger`. `R/sidecar.rs` starts only the sidecar, and `R/logger.rs` says no separate logger process is needed. One of the two must go. Needs a decision.
6. **Keep-awake and several macOS integrations have a setting or a name but no code.** `caffeinate_while_agents_running` exists in the registry. No Rust command, no Platform method and no backlog id implement it. The same holds for the zsh shell integration (`R/pty.rs` says "the UI writes it"; no UI file does), a navigation guard, window vibrancy, and the Full Disk Access check.
7. **Turns the Claude CLI starts by itself** (a finished background task wakes the agent) have no home. The turn tracker handles a foreign result during our turn only. New id AGENT-15.
8. **Two runtimes capture the login shell** (`R/shell.rs` PLAT-04 and `S/shell-env` SIDE-10). The rules need one test that compares their answers.
9. **The webview can reach any absolute path** through `fs_*` and `shell_run`. The capability file is small, but the custom commands have no allowed roots. New id PLAT-29.
10. **`getHealth` is defined and unused.** `P/rpc.ts` says the Rust launcher polls it. `R/sidecar.rs` says there is no health check.

## Proposed decision entries

The file headers already record these choices. `docs/decisions.md` does not, so a reader of the log cannot see them. Each needs a dated entry (the log is changed by new entries, never by edits).

1. **The sidecar has no HTTP server and no bearer token.** The socket is private to the user. Replaces Conductor's `/v1/health` and stdin bootstrap. Also settles `getHealth`.
2. **GitHub access is the user's own `gh` login, for the app and for agents.** No token broker, no `GH_TOKEN` per session.
3. **Approval answers: four, not five.** No "allow with suggested rules", no `auto` permission mode, no 300 s timeout on Codex prompts. Settle the registry keys `experimental_auto_permission_mode` and `codex_tool_approval_policy` in the same entry.
4. **ACP agents: OpenCode and Pi.** Muse and its MSP protocol are not built.
5. **One logger.** Either Rust writes the files (PLAT-18) and the sidecar logger mode goes, or the reverse.
6. **Wire and storage details that differ from Conductor:** acknowledgements in any order, outbox file names from the UTF-8 id, checkpoint refs under `refs/conducted/checkpoints`, no `state` on `user_message`, no separate error notification, own JSON-RPC error codes.
7. **Cancel:** the sidecar drops its in-memory queue, the app pauses its persistent queue and keeps what the user typed.
